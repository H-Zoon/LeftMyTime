# 눈금 글로우·초 표시·상세 콘텐츠 개선안

작성: 2026-09-21. 아래는 최초 조사·제안 기록이다. 후속 ‘진행’ 요청으로 앱 초 표시·공유 상세·글로우·위젯 기준 시각을 구현했다. **현재 구현/미완료 범위와 검증 상태는 [적용 기록](QA_TIME_DETAIL_2026-09-21.md)을 따른다.** 위젯 초 카운트다운은 활성화하지 않았다.

요청: 남은 눈금 뒤 글로우, 시간 구간·오늘의 앱/위젯 초 단위 갱신, 상세 시트의 유용한 정보 보강. 정밀도 질문에서 사용자가 **“1초 단위 시간 + 경과율 소수점 한 자리”**를 선택했다. 0.1초 카운트다운은 포함하지 않는다.

## 결론과 순서

| 구분 | 권장 방향 | 적용 조건 |
| --- | --- | --- |
| 글로우 | 남은 눈금 바로 뒤에만 강조색으로 낮은 농도의 빛 표시 | A안의 장식 금지 규칙에 용도가 제한된 예외를 실제 사용처와 함께 기록 |
| 앱의 시간 구간·오늘 | 기존 1초 계산 흐름을 재사용해 초를 실제로 표시 | 초가 추가된 폭·줄바꿈, 종료/자정 경계 확인 |
| 상세 내용 | 남은 시간 → 눈금·경과율 → 기간 정보 → 시간에 맞는 재미있는 아이디어 | 기간 시트와 위젯 상세에서 같은 표시 데이터·구성요소 사용 |
| 위젯의 시간 구간·오늘 | 시스템 Chronometer를 후보로 검증하고 종료·눈금 동기화도 해결 | 숫자만 움직이는 상태를 기능 완료로 처리하지 않음 |

앱의 초 표시·상세 보강을 먼저 묶고, 글로우는 앱과 위젯에서 같은 규칙으로 적용한다. 위젯 카운트다운은 별도 기능 작업으로 진행한다. 기존 단일 4×2·요약 4×1 크기와 주요 배치는 유지하는 것을 목표로 한다.

## 현재 코드에서 확인한 점

| 위치 | 현재 동작 | 개선 의미 |
| --- | --- | --- |

| `RemainingTimeFormat.kt` | 시·분만 반환하고 60초 미만은 ‘1분 미만’ | 값은 갱신되지만 보이는 글자가 그대로인 직접 원인 |
| `RemainingTimeText.kt` | 공통 숫자/단위 규칙과 단위 묶음 줄바꿈 사용 | 호출 위치별 표시 정밀도를 추가 |
| `HeaderSection.kt` | 기간 시트는 큰 숫자·눈금·일수 설명·위젯 추가만 표시 | 홈과 다른 정보를 읽을 이유가 부족함 |
| `WidgetDetailsActivity.kt` | 화면이 보이는 동안 1초 계산하지만 같은 시·분 표현 사용 | 시트와 상세 콘텐츠를 공유할 수 있음 |
| `TimeRuler.kt` / `WidgetRendering.kt` | 앱은 Canvas, 위젯은 Bitmap으로 눈금 생성 | 좌표·색상·농도를 공유하고 각 렌더러에서 구현 가능 |
| `ItemGenerate.kt` / `WidgetPresentation.kt` | 경과율을 먼저 한 자리로 반올림하고 위젯에는 정수로 전달 | 숫자용 반올림과 눈금·글로우용 원비율 분리 필요 |
| 위젯 XML·갱신 경로 | 30분 주기와 수동/변경 이벤트 갱신 | 현재 숫자·눈금은 갱신 시점의 결과 |

현재 바텀시트는 오늘·달·년의 상세다. 개인 일정 목록은 펼친 행, 홈 대표 일정 제목은 편집으로 이동한다. 이 조사만으로 모든 개인 일정의 진입 방식을 바텀시트로 교체하지 않는다.

## 1. 남은 눈금 뒤 글로우

### 표현

- 경과 비율에 해당하는 위치부터 눈금 오른쪽 끝까지 빛을 둔다. 남은 시간이 줄면 폭도 줄어든다.
- 기존 팔레트의 강조색을 사용한다. 지난 눈금·숫자·화면 전체에는 빛을 추가하지 않는다.
- 기존 28dp 눈금 영역 안에서 감쇠하도록 한다. 숫자나 아래 시각 라벨까지 번지지 않게 해 위젯 높이를 늘리지 않는다.
- 최대 농도는 밝게 6–8%, 어둡게 10–12%를 **시작 후보**로 한다. 실제 화면에서 결정할 값이며 확정 토큰이 아니다.
- 위아래와 남은 영역의 양 끝에서 투명해진다. 위에 중립/강조 눈금을 선명하게 그린다.
- 깜빡임·호흡·반복 밝기 변화는 넣지 않는다. 실제 남은 구간 변화만 반영한다.
- 시작 전·종료·잘못된 기간·오류 상태는 활성 글로우를 숨긴다. 눈금 숨김 설정이면 함께 숨긴다.
- 남은 폭이 아주 작으면 자연스럽게 희미해진다. 최소 폭을 키워 남은 양을 과장하지 않는다.

A안의 ‘색으로 남은 부분을 구별한다’는 역할을 보강하는 제한된 예외다. 적용 시 `DESIGN_SYSTEM.md`와 `TimeRulerTokens`에 범위를 기록한다. 조사 단계에서 일반적인 그라데이션·그림자 허용으로 기준을 바꾸지는 않는다.

### 구현 비교

| 방법 | 장점 | 제약 | 판단 |
| --- | --- | --- | --- |
| 눈금 복제 후 blur | 광원처럼 번짐 | Compose blur는 Android 12 이상. 구형·위젯에 별도 처리 필요 | 우선순위 낮음 |
| 투명도로 감쇠하는 그라데이션 | Compose와 Bitmap Canvas에 같은 형태 적용 가능 | 형태·농도를 직접 맞춰야 함 | **권장** |
| 넓은 카드/화면 그림자 | 일부 구현이 단순함 | 남은 양과 무관하고 위계가 흐려짐 | 제외 |

Compose Brush와 Bitmap Canvas의 그라데이션을 사용한다는 제안이다. 공식 API에 근거한 방안이며 실제 렌더링은 아직 확인하지 않았다. [Compose Brush](https://developer.android.com/develop/ui/compose/graphics/draw/brush), [blur 지원 범위](https://developer.android.com/develop/ui/compose/graphics/images/customize#blur-image)

눈금·빛에는 반올림 전 경과 비율을 전달하고 퍼센트 문구만 마지막에 포맷한다. 완료 상태를 `percent == 100`으로 추측하지 않는다. 위젯 글로우는 현재 갱신 시점의 비율이므로 초 단위로 움직인다고 설명하지 않는다.

## 2. 초 단위 표시

### 앱

| 영역 | 표시 제안 |
| --- | --- |
| 홈 대표 시간 구간 | `1시간 12분 08초 남음`. 시·분은 현재 위계, 초는 보조 숫자 위계 |
| 홈 상단 오늘 | 시·분에 작은 초를 붙임. 세 기간의 주 숫자 22sp 위계 유지. 좁으면 단위 묶음 줄바꿈 |
| 오늘·시간 구간 상세 | 초까지 포함한 남은 시간과 `62.5% 지남` |
| 이번 달·올해 | 기존 일수 유지. 경과율은 현재 계산과 같은 **일수 기준**임을 설명 |
| 접힌 개인 일정 목록 | 여러 값이 동시에 움직이지 않도록 기존 분/일 중심 표현 유지 |

초는 `08 → 07 → 06`처럼 두 자리 폭을 유지한다. 분·시의 자리 변화에도 단위 묶음이 흔들리지 않도록 실제 폰트와 공간을 확인한다. 초마다 숫자가 날아들거나 화면 전체가 다시 등장하는 애니메이션은 추가하지 않는다. 1분 미만은 `42초`처럼 표시한다.

`RemainingTimeText`와 공유 포맷 함수에 정밀도를 명시적으로 전달한다. 전체 포맷 함수를 일괄 변경하면 위젯·목록·요약 폭까지 영향을 주므로 호출 위치별로 적용한다. 새로운 서체·팔레트를 도입하지 않는다.

기존 1초 흐름을 재사용하고 기준 시각과 현재 시각의 차이로 값을 계산한다. 이전 숫자에서 1씩 빼는 누적 방식은 사용하지 않는다. 앱 복귀 때 즉시 맞추고 화면을 떠나면 기존 생명주기 제어를 따른다. 매초 DB 저장·알림 재예약·위젯 전체 갱신을 연결하지 않는다.

오늘의 기존 기준은 00:00–23:59:59다. 양의 1초 미만을 0초로 내릴 수 있으므로 마지막 순간의 ‘진행 중 0초’와 자정을 반드시 확인한다. 표시 올림 여부는 실제 종료 시각으로 판단하며 모든 `remainingSeconds`에 1을 더하는 식으로 보정하지 않는다.

퍼센트 소수점 한 자리는 매초 바뀌지 않는다. 24시간의 0.1%는 86.4초다. 작동 여부는 초 숫자로 전달한다. 달·년은 현재 일수 계산을 유지하므로 초 카운트다운으로 임의 환산하지 않는다. 완료 여부는 반올림된 100.0%로 추측하지 않는다.

접근성에서는 초마다 강제 음성 알림을 보내지 않는다. 초점으로 읽을 때 현재 남은 시간·상태를 제공하고 종료·다음 구간 전환 같은 의미 있는 변화만 별도로 검토한다.

### 위젯

provider 주기는 30분 미만으로 설정할 수 없다. WorkManager 주기 작업도 최소 15분으로 정밀 시계의 대체가 아니다. 위젯 전체를 매초 다시 보내는 방식은 실행 제약과 비용 때문에 권장하지 않는다. [위젯 갱신 지침](https://developer.android.com/develop/ui/views/appwidgets/advanced), [예약 작업과 알람](https://developer.android.com/develop/background-work/services/alarms)

`RemoteViews.setChronometerCountDown`은 API 24부터 지원하고 앱 최소 API는 26이다. 런처에서 초를 갱신하므로 앱 프로세스의 1초 작업 없이 숫자를 움직일 수 있는 후보다. **숫자 지원과 위젯 전체의 실시간 동작은 구분한다.** [RemoteViews API](https://developer.android.com/reference/android/widget/RemoteViews#setChronometerCountDown(int,%20boolean))

Android SDK 36 소스와 AOSP에서 확인한 제약:

- 0초에 자동 정지하지 않고 음수로 계속 흐른다.
- 완성된 시간 문자열을 `%s`로 받으므로 숫자·한글 단위를 따로 꾸미는 현재 형태를 그대로 옮길 수 없다. `1:12:08`과 별도 상태 문구를 검토해야 한다.
- 시스템 tick으로 앱의 일정 선택·경과율·Bitmap 눈금이 다시 계산되지는 않는다.
- 기준은 `elapsedRealtime` 시간축이다. 기기 시각·시간대 변경, 재부팅 후 실제 종료 시각에서 기준을 다시 만들어야 한다.

[AOSP Chronometer 구현](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/widget/Chronometer.java)

**기술 검증 제안:** 오늘과 진행 중인 고정 시간 일정의 단일 4×2부터 `Chronometer 숫자 + 시작/종료 경계 재계산`을 확인한다. 시작까지, 자동 다음 일정, 자정, 요약 4×1로 검증을 확장한다. 시계 표기에도 기존 산세리프·글자색·간격을 사용한다.

현재 `ReminderScheduler`는 부정확 알람을 사용하며 정확한 알람 권한은 없다. 기존 알림에 연결하는 것만으로 종료 갱신이 보장되지 않는다. 정확한 경계가 필요한 방식은 권한 거부/회수·절전까지 설계해야 한다. 이번 조사에서 상시 서비스나 권한을 추가하지 않는다. [정확한 알람 조건](https://developer.android.com/develop/background-work/services/alarms#exact-permission-declare)

숫자는 움직이는데 지난 눈금·글로우가 남는 문제도 해결 대상이다. 눈금 경계별 갱신을 시도하더라도 실행 지연을 확인해야 한다. 종료 상태와 눈금의 일관성 확보 전에는 기존 위젯에 초만 켜서 배포하지 않는다.

검증 전 보완책은 마지막 갱신 시각과 새로고침 동작을 명확히 하는 것이다. 기존 보조 정보 자리에서 공간을 검토하며 실시간 기능의 완성안으로 취급하지 않는다. 현재 시각만 움직이는 시계를 남은 시간의 실시간 갱신처럼 사용하지 않는다.

## 3. 상세 시트

### 정보 순서

1. 기간/일정 이름과 상태.
2. 남은 시간. 오늘·시간 구간은 초까지, 달·년·날짜는 기존 일수 의미 유지.
3. 눈금과 `62.5% 지남 · 37.5% 남음`. 같은 기준값에서 파생하고 한 자리로 표시.
4. 시작·종료, 전체 길이와 지나간 길이. 반복 정보는 합친다.
5. **‘이 시간이면’**: 활동이나 시간의 길이를 재미있게 이해하는 문장 1–2개.
6. 기존 위젯 추가. 개인 일정 상세의 편집 동선 유지.

구분선과 간격으로 묶고 통계마다 카드·아이콘·색 배지를 추가하지 않는다. 긴 내용은 기존 시트 스크롤을 사용하고 큰 글자를 축소하지 않는다.

시간 구간 상세의 내용 예시(실제 화면/데이터 아님):

> 오후 집중 시간 · 14:00–16:00\
> **45분 00초 남음**\
> 62.5% 지남 · 37.5% 남음\
> 전체 2시간 중 1시간 15분 경과\
>
> **이 시간이면**\
> 3분짜리 노래 15곡으로 작은 플레이리스트 완주.\
> 또는 15분을 잡고 종이비행기 3종 비행 대회.\
> 다른 아이디어 보기

| 남은 길이 | 문구 후보 | 기준 |
| --- | --- | --- |
| 12분 | ‘3분짜리 노래 4곡. 짧은 방구석 콘서트.’ | 곡당 3분 가정을 문구에 포함 |
| 45분 | ‘15분짜리 낙서 시간 세 번. 마지막 그림에는 제목도 붙이기.’ | 15분 × 3 |
| 2시간 | ‘90분 영화를 고르면, 끝나고 30분은 나만의 영화 평론가.’ | 영화 길이 조건 명시 |
| 7일 | ‘하루 한 장, 7장의 하늘 사진전.’ | 날짜마다 하나씩 모으는 예시 |
| 30일 | ‘하루 한 곡, 30곡짜리 이번 달 사운드트랙.’ | 남은 일수와 제안 수 연결 |
| 100일 | ‘7일마다 같은 장소 한 장. 14장으로 계절 변화 모으기.’ | 100 ÷ 7 내림 |

제품에 넣을 수 있는 창작 문구 후보로, 소요 시간·결과를 보장하는 안내가 아니다. 재미·휴식·작은 시도를 섞고 남은 시간을 모두 채우라는 압박을 피한다. 여러 문장은 대안이며 모두 수행하라는 목록으로 제시하지 않는다.

### 동작과 재사용

- 로컬 문구 묶음과 남은 길이 조건으로 시작한다. 일정 제목을 외부 AI에 보내거나 네트워크 응답을 기다릴 필요가 없다.
- 유형·남은 길이·시작 전/진행 중/종료 상태를 명시적으로 입력받는다. 표시 문자열에서 상태를 추측하지 않는다.
- 시트를 읽는 동안 문구 선택을 유지한다. 새로 열거나 ‘다른 아이디어 보기’를 누를 때 바꾼다. 초 갱신마다 임의 선택하지 않는다.
- 더 이상 남은 길이에 맞지 않으면 짧은 후보로 한 번 전환한다. 여유를 둔 선택 조건으로 경계에서 연속 교체되지 않게 한다.
- 횟수는 내림하고 0회 후보는 제외한다. 긴 기간에는 과도한 환산 수치보다 날짜별 작은 시도 유형을 우선한다.
- 시작 전이면 ‘시작 전, 이 시간이면’으로 구분한다. 종료된 기간에는 활동을 권하지 않는다. 일일 구간의 다음 시작과 완료된 날짜를 구분한다.
- ‘오늘 제외 N일’은 자유시간 N×24시간을 뜻하지 않는다. 날짜 항목에는 하루 한 번 같은 제안을 사용한다.
- 문구·복수형은 한/영 문자열 리소스로 관리하고 예시 일정은 제품 기본 데이터에 넣지 않는다.

`RemainingTimeText`, `TimeRuler`, `PinWidgetButton`, Theme/Spacing을 재사용한다. 기간 시트와 `WidgetDetailsActivity`에서 쓸 공통 상세 콘텐츠와 활동 선택 로직을 분리한다. 원본 값·기간 종류·상태를 전달하고 경과 시간은 반올림된 퍼센트에서 역산하지 않는다.

진행률 설정은 전체/막대만/숨김이 있다. 전체에서는 눈금·비율, 막대만에서는 눈금, 숨김에서는 둘 다 숨기는 기준을 상세에도 적용하는 안이다. 시간 정보·아이디어는 유지한다. 기존 설정 문구·사용처의 호환 여부를 구현 때 함께 확인한다.

## 적용 시 검증 조건

- 밝게/어둡게·5개 팔레트·0/중간/종료 직전 폭·눈금 숨김. 글로우가 숫자 대비를 해치지 않는지 확인.
- 320dp·큰 글자 1.3/2.0·긴 한/영 제목과 숫자. 초 생략이나 숫자 축소로 맞추지 않음.
- 1시간→59분59초, 1분→59초, 마지막 1초, 종료·다음 시작·자정. 0초와 반올림된 100.0%를 완료로 오해하지 않는지 확인.
- 월말·윤년·연말·시간대/수동 시각 변경·앱 복귀. 월·년은 기존 일수 기준 유지.
- 위젯의 프로세스 종료·화면 끄기·절전·재부팅·권한 변화·여러 설치·Pixel/One UI. 숫자/눈금/상태와 단일 4×2·요약 4×1을 각각 확인.
- 아이디어의 안정성·길이 조건·종료/빈 상태/삭제, TalkBack·초점 복귀·48dp 영역·매초 강제 낭독 없음.
- 사용자 최종 검증 요청 시 포맷·선택·날짜/종료 경계를 검증하고 `testDebugUnitTest assembleDebug lintDebug` 실행. 기존 경고와 새 문제 구분.

이번 조사는 저장소 코드, 설치된 Android SDK 소스, Android 공식 문서/AOSP를 근거로 한다. **앱 코드 변경, 빌드·Lint·단위 테스트, 새 APK 설치, 화면·절전 동작 검증은 수행하지 않았다.** 정밀도 선택 외 시각 수치·콘텐츠는 제안이며 확정 디자인 토큰이나 완료 기능으로 취급하지 않는다.
