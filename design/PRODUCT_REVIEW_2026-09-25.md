# LeftMyTime 종합 평가와 개선 가능성 — 2026-09-25

대상: `b3be475`의 제품 코드와 디자인 기준. 요청은 종합 평가·사용자 경험 개선·추가 기능의 가능성 검토이며 **이번에는 제품 코드를 수정하지 않았다.**

후속 범위 결정(2026-09-26): 사용자가 기기 간 동기화(F13)는 필요하지 않다고 결정해 구현 범위에서 제외했다. 아래 후보 표는 당시 조사 기록이며 현재 할 일 목록이 아니다. 파일 백업·복구는 유지한다. 최신 구현 상태는 [종합 개선 적용 현황](IMPROVEMENT_IMPLEMENTATION_2026-09-25.md)을 따른다.

## 판단

**‘남은 시간을 한눈에 이해한다’는 정체성과 디자인 기준은 잡혔다. 다음 투자 우선순위는 알림·데이터의 신뢰성, 짧은 구간을 시작하는 편의성, 테마 비교 동선이다.**

큰 숫자·남은 눈금·오늘/달/년 요약이 같은 의미를 전달하고 일반 위젯도 이 표현을 따른다. 시간 이야기와 눈금 탐색은 상세를 열었을 때의 보상으로 잘 맞는다. 앞으로 재미 요소는 이 상세 영역에서 확장하고 홈의 읽기 부담은 유지하는 편이 좋다.

평가는 저장소와 제한된 에뮬레이터 사용에 근거한다. 고객 리뷰·이용률·이탈률·Firebase 콘솔·스토어 경쟁 현황은 확인하지 않았다. 사용자에게 들은 주요 용도는 업무·공부의 짧은 시간과 하루·달·년이다. 인기 원인·시장 유일성·개선 후 유지율을 검증된 사실로 주장하지 않는다.

## 우선 개선할 사용자 문제

우선순위는 제품 관점의 제안이다. ‘실행 확인’과 ‘코드 확인’을 구분한다. 이번 리뷰에서 아래 문제를 수정하지 않았다.

### R1. 권한을 끈 상태에서 편집하면 기존 알림 선택을 잃을 수 있음 — 높음

- 코드 확인: `ItemEditorScreen.kt:232`는 기존 항목을 읽을 때 알림을 사용할 수 없으면 저장된 offset 대신 비활성 값을 초안에 넣는다. `ItemEditorActivity.kt:102`도 권한이 없으면 비활성 값으로 저장한다.
- 조건: 알림이 설정된 일정 → 시스템 알림 끄기 → 제목만 수정·저장 → 시스템 알림 다시 켜기. 원래 알림 선택이 사라지는 코드 경로다. 이번 기기에서 권한 전환 시나리오를 실제 재현하지는 않았다.
- 개선: **사용자가 선택한 알림 설정과 지금 알림을 보낼 수 있는 상태를 분리**한다. 원래 선택을 보존하고 ‘기기에서 알림이 꺼져 있음’을 표시하며 예약만 보류한다. 명시적으로 ‘알림 없음’을 고를 때만 저장값을 바꾼다.
- 가능성/비용: 가능, 중간. 기존 저장 필드를 유지할 수 있고 권한 복귀 시 예약 복원까지 검증해야 한다.

### R2. 반복 날짜 알림·시간대 변경·알림 진입 경로 정리 — 높음

- 코드 확인: `ReminderReceiver.kt:55`는 시간 구간만 다음 알림을 예약한다. 반복 날짜의 다음 회차는 홈/위젯/부팅에서 데이터를 읽으며 넘어간다. 앱을 열지 않고 해당 위젯도 없으면 다음 회차의 날짜 알림을 예약하는 경로가 없다.
- 알림용 `BootReceiver`는 부팅만 처리한다. `TIME_SET`/`TIMEZONE_CHANGED`는 위젯 수신기에 연결돼 있고 위젯 렌더링에서 전체 알림을 재예약하지 않는다. 시간대 변경 후 기존 현지 시각 알림의 재계산이 필요하다. 실제 시간대 변경·장기 반복 수신은 미검증이다.
- 알림을 누르면 `MainActivity`만 열며 일정 ID를 전달하지 않는다(`ReminderReceiver.kt:40`). 대상 상세로 바로 연결할 수 있다.
- 개선: 화면 표시와 독립적인 반복/예약 정책을 마련하고 부팅·시간대/시각 변경·권한 복귀에서 같은 예약 처리를 사용한다. 현재/다음 회차를 구분해 누락·중복을 막고 공통 상세를 알림에서도 재사용한다.
- 현재 `setAndAllowWhileIdle`는 정확한 시각 도착을 보장하는 방식이 아니다. 안내와 예약 복원을 먼저 정리하고, 정확한 종료 알림을 기능으로 제공할 때 특별 접근 권한과 거부 시 동작을 별도 설계한다. [Android 알람 기준](https://developer.android.com/develop/background-work/services/alarms)
- 가능성/비용: 가능, 중간~큼. 앱 미실행·재부팅·일광절약시간·자정·중복 수신 검증이 필요하다.

### R3. 사용자 주도의 백업·복구 제공 — 높음

- 코드 확인: 매니페스트는 `allowBackup=false`, `fullBackupContent=false`이고 자체 내보내기/복구 UI는 없다. 기기 교체나 실수 삭제에 대비해 직접 복구할 경로가 부족하다.
- 개선: 버전이 있는 내보내기 파일 → 복구 미리보기 → 병합/추가와 충돌 처리 → 저장 완료 후 알림 재예약. 설치 위젯의 호스트 ID를 다른 기기에 그대로 옮기지 않는다.
- 가능성/비용: 가능, 중간. 첫 단계는 계정/서버 없이 시스템 파일 선택기를 이용할 수 있다. 잘못된 파일·이전 형식·부분 실패·중복 복구를 다뤄야 한다. [문서 생성·열기 API](https://developer.android.com/training/data-storage/shared/documents-files)
- Android 12 이상 일부 제조사의 기기 간 이전은 `allowBackup=false`와 별도로 동작할 수 있다. ‘모든 기기에서 이전 불가능’ 대신 **앱이 직접 제공하는 복구 수단 부재**로 평가한다. [Auto Backup 안내](https://developer.android.com/identity/data/autobackup)

### R4. 짧은 시간 등록 부담과 자정 경계 — 높음

- 실행 확인: 제목·시작·종료·저장 흐름이며 ‘지금 25분’ 같은 일회성 시작 동작은 없다.
- 코드 확인: 시간 항목은 날짜 없는 매일의 구간이고 `end > start`만 허용한다(`TimeRangeSnapshot.kt`, `ItemEditorScreen.kt:929`). 23:50부터 다음 날 00:15까지를 지원하지 않는다. 23시 이후 기본 ‘현재부터 1시간’도 종료가 다음 날로 넘어가면 검증에 걸리는 구조다. 해당 야간 입력은 실행 재현하지 않았다.
- 개선: 기존 매일 구간을 보존하고 **일회성 집중 세션**을 별도 의미로 제공한다. 15/25/50분·직접 입력, 기본 제목, 종료 후 정리까지 다룬다. 자정 넘김은 원본 시작/종료 날짜 또는 명시적 다음 날 관계로 표현한다.
- 가능성/비용: 가능, 중간~큼. 버튼으로 시각만 채우면 매일 다시 시작하는 뜻이 되므로 신규 기능으로는 불충분하다. 세션 상태·복구·위젯·알림을 함께 설계한다. 일시정지/재개와 통계는 후속으로 분리할 수 있다.

### R5. 테마를 고르는 동안 결과를 보기 어려움 — 중간

- 실행 확인: 일반 폭에서도 선택 도구가 위쪽 공간을 많이 차지한다. 320dp×720dp, 한국어, 글자 1.5배에서는 첫 화면에 앱 견본이 전혀 보이지 않았다. `ThemePreviewScreen.kt:62`의 선택 영역 뒤 `:103`에 견본이 위치한다.
- 개선: 실제 대표 숫자·눈금 견본을 먼저 볼 수 있게 하고 색상/모드 선택은 간결한 영역이나 펼치는 패널로 묶는다. 글자를 축소하거나 홈을 통째로 작은 이미지로 대체하지 않는다. 적용/취소 구조는 유지한다.
- 가능성/비용: 가능, 작음~중간. 기존 화면과 표시 컴포넌트를 재사용한다. ‘선택 → 결과 확인 → 다음 선택’의 스크롤 왕복 감소가 완료 기준이다.

### R6. 편집 내용 보호와 시간 표기 통일 — 중간

- 실행 확인: 임시 일정 `ReviewF`를 `ReviewFDraft`로 편집한 뒤 상단 뒤로를 누르면 안내 없이 홈으로 나가며 원래 제목이 유지됐다. 수정 내용을 잃을 수 있다. 회전 복원용 `rememberSaveable`은 화면을 닫은 뒤 초안 보존과 다르다.
- 개선: 변경 여부를 비교해 초안 복구를 제공하거나 변경이 있을 때만 이탈 확인을 한다. 저장 중 이탈·반복 저장도 함께 다룬다.
- 실행 확인: 같은 영어 12시간제 기기에서 편집은 `10:44 PM`, 홈/목록/눈금은 `22:44`, 상세 현재 위치는 다시 AM/PM으로 표시됐다. `ItemGenerate.kt:242`의 고정 형식과 기기 형식이 섞여 있다.
- 개선: 저장 형식과 표시 형식을 분리한 공통 포매터로 기기 12/24시간·로케일을 따른다.
- 가능성/비용: 가능, 작음~중간. 계산·저장 형식을 바꾸지 않고 개선할 수 있다.

### R7. 위젯의 ‘실시간’ 기대 관리 — 중간, 기술 검증 필요

- 실행 확인: 설치 위젯에 기준 날짜·시간, 남은 분, 눈금·범위 라벨이 보이고 탭하면 같은 일정의 상세가 열린다. 새 일반 위젯의 Pixel 기본 안내는 4×2였다.
- 코드 확인: XML은 30분 주기이고 숫자·눈금은 갱신 시점 값이다. 조작·앱 진입·방송에 의한 별도 갱신도 있어 ‘항상 30분 동안 고정’이라고 단정하지 않는다. 주기를 1초로 줄이는 것으로 해결되지 않는다. [위젯 갱신 제약](https://developer.android.com/develop/ui/views/appwidgets/advanced)
- 개선: 기준 시각과 상세 연결은 유지한다. 선택형 실시간 숫자는 `Chronometer` 카운트다운을 기술 검증할 수 있다. 종료 후 음수, 시작/진행/종료 전환, 날짜·눈금과 숫자의 기준 불일치를 해소해야 제공한다. [RemoteViews 카운트다운 API](https://developer.android.com/reference/android/widget/RemoteViews#setChronometerCountDown(int,%20boolean))
- 가능성/비용: 숫자 자동 감소는 조건부 가능, 중간~큼. 눈금까지 매초 정확하게 움직이는 일반 위젯을 기본 약속으로 삼지 않는다. 기존 4×2/4×1과 배터리 영향을 함께 검증한다.

캘린더는 Android Calendar Provider로 접근할 수 있으나 복잡한 반복·예외·시간대의 앱 모델 매핑이 주요 비용이다. [Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)

우선순위가 낮은 후보는 공개 순위·연속 출석 압박·상시 장식 애니메이션·출처 없는 즉석 AI 이야기다. 현재 핵심 동기와 사용자 반응에 근거해 정확한 남은 시간과 출처 있는 이야기의 품질을 먼저 유지하는 판단이다.

## AI와 장기 운영을 위한 작업 기준

1. 기존 디자인 문서와 실제 공통 컴포넌트를 기준으로 사용한다. 테마마다 지원 화면·위젯·큰 글자·빈/오류 상태를 함께 완료한다.
2. 반복/알림 예약이 화면 표시의 데이터 읽기에 의존하는 경계를 정리한다. 미리보기를 위해 별도 읽기 전용 ViewModel이 필요했던 이유처럼 조회에 저장·예약이 섞이면 확장 때 실수하기 쉽다. 전면 재작성 대신 반복·예약부터 분리한다.
3. 홈에도 조회 중·실패·재시도를 구분한다. 현재 ViewModel은 빈 목록으로 시작하며 정상 데이터 흐름의 예외 표시가 별도로 없다. 한 항목의 잘못된 날짜·저장소 실패가 전체 표시를 막는 조건을 검증한다. 이번에 오류를 강제로 주입하지는 않았다.
4. 날짜/자정/윤년/반복·예약·복구는 자동 검증, 홈/상세/설정/위젯은 밝기·320dp·큰 글자·긴 제목 실제 렌더링 검수로 나눈다. 빌드 성공을 테스트 통과나 출시 승인으로 확대하지 않는다.
5. Firebase 의존성과 실제 수집을 구분한다. 명시적 `logEvent`는 발견하지 못했다. 기존 콘솔/동의를 확인한 후 필요하면 생성 시작→완료, 위젯 설정 완료, 테마 적용/취소, 기능 재사용을 최소한으로 측정한다. 제목·내용·정확한 일정 날짜를 이벤트에 넣지 않는다.
6. 작게 묶어 전후 비교한다. 가설은 ‘바로 시작이 초기 등록 시간을 줄이는가’, ‘테마 선택 후 스크롤 왕복이 줄었는가’처럼 둔다. 목표 수치와 기준선은 실제 측정 후 정한다.
