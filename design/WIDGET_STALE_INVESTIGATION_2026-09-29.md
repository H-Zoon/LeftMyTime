# 위젯 장시간 미갱신 조사

2026-10-05 후속: 사용자는 문제가 **기존 설치 앱**에서 발생했다고 확인했다. 마지막 커밋의 보완을 아직 설치하지 않은 상태이며, 추가 코드 분석·복구 수정과 최신 미검증 범위는 [10월 5일 기록](WIDGET_REFRESH_RECOVERY_2026-10-05.md)을 따른다.

2026-09-29 사용자 보고: 3시간이 지나도 위젯이 갱신되지 않아 실제 남은 시간과 큰 차이 발생.
**자동 갱신 보완 코드를 반영했으며 빌드·재현 검증 전이다.** 초 단위 지원 확대와 별개의 기존 위젯 갱신 문제로 다룬다. 아래 초기 조사 뒤의 구현 절이 최신 상태다.

## 수정 전 코드에서 확인한 상태

- 모든 provider XML의 `updatePeriodMillis`는 1,800,000ms(30분)다. 30분은 정확한 갱신 시각 보장이 아니다.
- 초 옵션 미지원/꺼짐 위젯은 게시 시점의 TextView 값과 눈금 이미지를 유지한다. 다음 게시 없이 시간값이 변하지 않는다.
- 일반 정기 갱신과 수동 새로고침은 같은 `AppWidget.onUpdate`→`renderWidget` 경로를 사용하며, `goAsync()`를 게시 완료까지 유지한다.
- `ItemGenerate.timeItem()`은 호출 때마다 현재 시간을 읽는다. 싱글턴에 이전 시간을 저장해 재사용하는 코드는 아니다.
- 정적 위젯은 `WidgetBoundarySchedule.record(..., null)`로 별도 경계 예약이 없어, 일반 정기 방송 및 앱/설정/데이터 변경 등에 의존한다. 자체적인 주기 갱신 복구 경로는 없다.
- `MainActivity.onResume`은 전체 위젯을 갱신하지만, `WidgetDetailsActivity`는 만료된 초 표시 링크 외에는 원래 위젯을 갱신하지 않는다. 상세에 들어가 최신 숫자를 보더라도 기존 위젯은 그대로일 수 있다. 이 누락만으로 3시간 자동 갱신 실패의 원인이 설명되지는 않는다.
- 여러 위젯 순차 게시에서 예외가 나면 뒤의 위젯 게시도 중단될 수 있다. 해당 오류가 이번 기기에서 발생했다는 증거는 없다.

## 연결 기기 읽기 전용 확인

- Samsung SM-A336N, Android 15, 앱 6.5(22), 마지막 업데이트 2026-09-28 13:37.
- One UI 런처에 LargeAppWidget/AppWidget/ScheduleAppWidget 세 개 등록. 각 provider의 실제 등록 주기도 30분.
- 확인 시 강제 중지/중지 패키지 아님. standby bucket 10(active), RUN_ANY_IN_BACKGROUND 기본 allow.
- 확인 시 충전 중·화면 꺼짐, Doze 및 Light Doze는 ACTIVE. 이 한 시점의 상태로 신고된 지난 3시간의 절전 상태까지 추정하지 않는다.
- 시스템 APPWIDGET_UPDATE 반복 알람(30분 간격)은 존재. 삼성 시스템 공통 알람이므로 이 사실만으로 이 앱의 각 provider에 실제 전달됐다고 판단하지 않는다.
- 최근 방송 이력에 2026-09-29 18:08:00의 AppWidget 대상 수동 새로고침 PendingIntent 방송이 있고 약33ms에 종료했다. 이는 방송 처리 기록이며 화면의 숫자 변경을 확인한 것은 아니다.
- 최근 앱 로그에서 이 정지 현상을 설명하는 Kotlin 예외 스택/WidgetBoundary/WidgetSeconds 실패는 확인하지 못했다. 보관된 로그만으로 과거 오류가 없었다고 결론 내리지 않는다.
- 기기의 설정·절전 정책·화면·위젯·앱 데이터 변경, 강제 방송·새 APK 설치는 수행하지 않았다.

## 남은 확인과 다음 조치

사용자 답변: **Android 15, 하루 요약, 새로고침을 누르면 갱신됨.** 자동 전달/실행/반영 경로를 우선 확인한다. 수동 갱신 성공은 모든 계산/렌더링 조건의 정상 동작이나 특정 OS 원인을 증명하지 않는다.

1. 문제 발생 시 위젯의 기준 시각과 현재 시각을 비교한다. 기간 요약은 기준 시각 표시가 없어 다른 위젯의 값과 혼동하지 않는다.
2. 수동 새로고침으로 바로 맞아지면 자동 전달/백그라운드 실행/런처 반영 경로를 좁힌다. 수동으로도 그대로면 계산·게시 오류와 런처 표시를 확인한다.
3. 자동 수신과 게시 성공을 구분할 수 있는 최소 로컬 진단이 필요하다. 도입 시 위젯 제목·내용·정확한 일정 날짜를 로그나 분석 이벤트에 기록하지 않는다. 현재 확인 가능한 기존 수집으로 과거 수신/게시 이력을 복구할 수는 없다.
4. 정적 위젯의 경계 예약 및 갱신 복구 설계, 위젯별 오류 격리, 상세 진입 시 갱신 누락을 검토한다. 반복 알람/WorkManager 추가만으로 Doze 중 정확한 주기나 홈 복귀 직후 갱신을 보장한다고 설명하지 않는다.

기존 [초 호환성 조사](WIDGET_SECONDS_COMPATIBILITY_2026-09-28.md)는 이 미갱신 문제를 해결한 기록이 아니다. 참고: [공식 위젯 갱신](https://developer.android.com/develop/ui/views/appwidgets/advanced), [Doze 제약](https://developer.android.com/training/monitoring-device-state/doze-standby).

초기 조사 시점에는 앱 코드 변경·빌드·Lint·단위/계측 테스트·새 화면 검수를 수행하지 않았다. 이후 코드 반영 범위는 아래와 같다.

## 답변 이후 자동 갱신 보완 — 미빌드

- 기존 `WidgetBoundarySchedule`/Receiver/렌더러를 재사용하여 **정적 오늘·기간 요약·시간 일정·이전 복합 요약**에 다음 15분 시점의 자체 갱신을 예약한다. 가까운 시작/종료 시각이 있으면 먼저 예약한다. 기존 시스템 30분 정기 갱신도 유지한다. 두 경로는 같은 Android 전력 제약을 받으며 독립적인 실행 보장을 제공하지 않는다.
- 이 예약은 기존의 **비기상·비정확 RTC 알람**이다. 15분은 요청 간격이며 실제 표시 지연의 상한이 아니다. 상시 서비스·매초 앱 IPC·새 권한·설정 키·DB/출시 버전 변경은 없다. 날짜만 표시하는 현대식 위젯은 새 15분 예약 대상에서 제외한다.
- 다른 위젯을 갱신할 때 기한이 지난 예약을 삭제하던 동작을 보완했다. 지난 예약은 해당 위젯이 게시되거나 제거될 때까지 보존하며 1분 뒤 재시도를 요청한다. 아직 미래인 시작/종료 경계를 임의로 1분 뒤로 미루지 않는다.
- 위젯 하나의 렌더링 실패가 나머지 위젯 갱신을 중단시키지 않도록 배치 처리에서 오류를 격리한다. 오류 종류만 로컬 Logcat에 기록하며 제목·내용·일정 날짜를 추가하지 않는다. 취소는 정상 전파한다.
- 일반 위젯 상세 화면의 `onResume`에서도 설치 위젯을 갱신한다. 기존 상세의 1초 UI 틱에 위젯 게시를 연결하지 않는다. 만료된 초 링크의 기존 갱신 경로는 유지한다.
- `WidgetSnapshotRefreshTest`에 정적 오늘/요약의 예약, 가까운 시작/종료 우선, 날짜 전용 제외, 지난 예약 보존과 가까운 미래 경계 보존 조건을 추가했다. **소스 추가이며 실행하지 않았다.**

이번 수정은 확인된 갱신 경로의 공백을 보완한다. 삼성의 원래 정기 갱신이 신고된 3시간 동안 왜 반영되지 않았는지는 아직 확정하지 못했다. 빌드/설치 후 Android15 One UI에서 앱을 닫고 3시간 이상 자동 갱신을 관찰해야 해결 여부를 판단할 수 있다. 화면 꺼짐/홈 복귀/Doze·다중 위젯·재부팅/시간 변경·위젯 삭제·예약 실패 복구·API37 초 표시 경계 회귀를 함께 검증한다.

이번에는 코드·문서 검토만 수행했다. 빌드·Lint·단위/계측 테스트와 설치·실화면 검수는 사용자 명시적 요청 전까지 미실행이다. 연결 휴대폰의 설치된 6.5에는 이 변경이 포함되지 않는다.
