# 위젯 초 단위 표시 적용안

작성일: 2026-09-26. 상태: **승인 후 선택형 1차 구현·검증 완료. 지원 범위 제한**.

현재 구현과 실제 검증 범위는 [실행 기록](QA_WIDGET_SECONDS_2026-09-26.md)이 우선한다. 아래 비교·단계는 승인 당시 계획이며 모든 대상의 지원 완료를 뜻하지 않는다. 오늘·7일 이내 시간 일정에 선택형 초 표시를 제공하고, 집중·기간 요약·날짜 일정은 기존 표시를 유지한다. Android 17/문서 버전9에서 실행 검증했고 Android 16/버전8은 정적으로 대체한다.

2026-09-26 구현 승인 후 기술 결정: Android 17 에뮬레이터의 실제 Pixel 런처(문서 버전9)에서 앱 프로세스 종료 후 독립적인 0초/종료 전환을 확인했다. 시간 속성의 연속 계산은 약30fps였고, 정수 epoch 차이와 초 시계 의존성으로 바꾼 시제품은 약39초에38프레임이었다. 공개 생성 편의 API만으로 필요한 연산을 구성할 수 없어, **공개 배포된 alpha20의 내부용 표시가 있는 생성 API를 버전 고정한 어댑터 한 곳에서 사용**하는 비용을 명시한다. Android의 숨겨진 API·리플렉션·자체 프로토콜 인코딩은 사용하지 않는다. 이는 초기 공개 API 우선 방침에 대한 구현상 예외이며, 선택형 실험 기능과 문서 버전9 이상 검사로 제한한다. 의존성 업그레이드 때 재검증이 필요하다. 제품 UI·Pixel 런처의 1차 실행 검증은 후속 기록에 있다. 다른 제조사 런처·장시간 전력·출시 검증 완료는 아니다.

조사 당시 사용자 요청은 위젯 초 단위 기능의 적용 방안 도출이었다. 이후 구현·검증을 명시적으로 승인했다. 이번 문서는 기존 A안과 선택형 시간 보드, 단일 4×2·기간 요약 4×1을 기준으로 한다. 기본 디자인을 유지한다. R7은 검증한 환경의 선택형 구현으로 진전했으며, 전체 환경 지원 완료는 아니다.

## 구현 전 승인안

이하의 미확인/제안 표현은 조사 당시의 기록이다. 현재 상태는 맨 위 실행 기록을 따른다.

## 권장 방향

**위젯을 표시하는 시스템이 초 숫자를 계산하고, 앱은 일정 변경과 시작·종료 경계에서 데이터를 전달하는 구조**를 권한다. 앱에서 매초 전체 위젯과 눈금 비트맵을 보내는 구조는 채택하지 않는다.

단, 기존 `Chronometer`는 종료 후 음수를 자체적으로 막지 못한다. 따라서 ‘0초 이후 정확한 종료 표시’를 출시 조건으로 삼는다면, **위젯 내부에서 남은 값과 상태를 함께 계산하는 Remote Compose 방식의 작은 기술 검증을 먼저 수행**한다. 성공한 OS·런처 범위에 선택형으로 제공하고, 지원하지 않는 환경에는 기존 기준 시각 표시를 유지한다.

Remote Compose의 실제 위젯 지원 범위·시간 연산·접근성·전력 사용은 아직 확인하지 않았다. **이 문서는 모든 기기에서 초 표시가 가능하다거나, Remote Compose로 해결됐다는 결론이 아니다.** 기존 Chronometer는 호환성 비교용 후보이며, 정확 알람만 추가하면 0초 문제가 해결된다고 판단하지 않는다.

## 현재 코드에서 확인한 것

- `WidgetRendering.kt`·`WidgetOverview.kt`는 게시 시점의 숫자를 TextView에 쓰고 눈금을 비트맵으로 전달한다. 단일 위젯은 기준 날짜·시각과 새로고침을 제공한다.
- 모든 provider의 정기 갱신 설정은 30분이다. 날짜·시간대 변경, 설정 변경, 수동 새로고침 등은 별도로 갱신한다.
- `AppWidget.kt`는 조회와 게시를 직렬화하며 실제 설정/추가 미리보기에 같은 렌더러를 사용한다. 새 실시간 경로에서도 미리보기는 고정 시각을 사용해야 한다.
- 집중 타이머는 `FocusClock`의 부팅 후 경과 시간과 부팅 식별값을 사용한다. 위젯 때문에 시스템 날짜 변경에 영향을 받는 타이머로 바꾸면 안 된다.
- `FocusReceiver`는 `goAsync()`를 사용하지만 `updateAllWidgets()`는 내부 갱신을 시작한 뒤 즉시 반환한다. 종료 방송의 보호 범위가 실제 위젯 게시까지 이어지도록 기다릴 수 있는 갱신 경로가 필요하다.
- 현재 minSdk 26, compileSdk/targetSdk 36이다. Remote Compose 의존성은 없다.

## 방식 비교와 기술 근거

| 방식 | 얻는 것 | 한계 | 판단 |
| --- | --- | --- | --- |
| 기존 RemoteViews + Chronometer + 경계 갱신 | 넓은 호환 범위, 매초 앱 실행 없이 숫자 표시, 기존 XML 대부분 재사용 | 0초 자동 정지 없음. 문구·눈금·다음 일정은 앱 갱신에 의존 | 비교용 시제품. 음수 없는 종료를 보장하는 출시안으로 단독 채택하지 않음 |
| Remote Compose + DrawInstructions | 호스트에서 시간에 따른 숫자·조건부 상태·눈금을 계산할 수 있는 후보 | 알파 라이브러리, 지원 연산/시계/런처 확인 필요, 별도 렌더러 작업 | 0초와 상태를 함께 처리하는 1차 기술 검증 대상으로 권장 |
| 앱에서 1초마다 RemoteViews 게시 | 표현을 앱이 직접 제어 | 앱 실행 유지·백그라운드 제한·빈번한 IPC와 비트맵 작업에 의존 | 채택하지 않음 |
| 현재 기준 시각 + 새로고침 + 상세 | 기존 호환성과 동작 보존 | 위젯 숫자가 실시간으로 움직이지 않음 | 미지원 환경의 대체 표시 |

`RemoteViews`는 Chronometer를 지원하며 사용자 정의 하위 클래스로 바꿀 수 없다. 따라서 앱 화면에서처럼 직접 만든 타이머 View를 넣어 tick마다 0으로 제한할 수 없다. [RemoteViews API](https://developer.android.com/reference/android/widget/RemoteViews)

Chronometer의 기준은 `elapsedRealtime`이고 기본 시간 표현은 `MM:SS` 또는 `H:MM:SS`다. AOSP 구현은 0 이후 음수 길이를 표시하며 원격 tick listener를 제공하지 않는다. 화면에서 숨겨졌을 때의 실행 제어도 호스트가 맡는다. 이는 소스 동작 확인이며 실제 제조사별 검수 결과는 아니다. [Chronometer API](https://developer.android.com/reference/android/widget/Chronometer), [AOSP 구현](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/widget/Chronometer.java)

30분 제한은 `updatePeriodMillis`에 해당한다. 이벤트 갱신 전체를 30분마다만 할 수 있다는 의미가 아니다. 다만 방송과 백그라운드 실행은 지연될 수 있다. 정확 알람도 권한·절전 조건을 고려해야 하며, 유휴 중 허용 알람에는 앱당 빈도 제한이 있다. 동시에 여러 위젯이 종료하는 경우까지 알람만으로 음수 방지를 약속할 수 없다. [위젯 갱신](https://developer.android.com/develop/ui/views/appwidgets/advanced), [알람 예약](https://developer.android.com/develop/background-work/services/alarms), [Doze 제약](https://developer.android.com/training/monitoring-device-state/doze-standby)

DrawInstructions API는 35부터 존재하고 지원 버전을 조회할 수 있다. 이것만으로 Android 15 이상 전체가 필요한 시간 연산을 지원한다고 결론 내리면 안 된다. XML과 그리기 명령 방식은 같은 RemoteViews 트리에서 섞을 수 없어, 숫자 한 칸만 새 방식으로 끼워 넣는 변경도 아니다. [DrawInstructions API](https://developer.android.com/reference/android/widget/RemoteViews.DrawInstructions), [RemoteViews 생성자](https://developer.android.com/reference/android/widget/RemoteViews#RemoteViews(android.widget.RemoteViews.DrawInstructions))

2026-09-26 확인 시 Remote Compose의 최신 공개 버전은 1.0.0-alpha20이다. 최신 소스에는 플랫폼 위젯용 프로파일과 제한된 연산 목록이 있고 일부 생성 API는 라이브러리 내부용으로 제한돼 있다. AndroidX의 내장 플레이어에서 실행된다는 사실을 홈 런처 지원으로 대체하면 안 된다. 특정 버전을 고정하고 공개 API·지원 프로파일로 생성할 수 있는지 먼저 확인한다. [공식 릴리스](https://developer.android.com/jetpack/androidx/releases/compose-remote), [위젯 프로파일 소스](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/remote/remote-creation/src/androidMain/java/androidx/compose/remote/creation/profile/RcPlatformProfiles.java)

시간 속성 소스에는 목표 시각에서 현재 시각을 빼는 연산이 있다. 이를 값 제한·조건부 표시와 조합하는 것이 제안의 근거다. 반면 `ContinuousSec`는 이름과 달리 매시간 순환하는 값이므로 집중 타이머의 부팅 후 경과 시간으로 사용할 수 없다. 필요한 연산이 실제 대상 프로파일에 포함되는지는 시제품에서 별도로 확인한다. [시간 연산 정의](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/remote/remote-creation-core/src/main/java/androidx/compose/remote/creation/Rc.java)

## 사용자에게 제공할 범위

| 대상 | 권장 표시·도입 순서 |
| --- | --- |
| 고정된 일회성 시간 일정 4×2 | 첫 시제품. 시작 전 → 진행 중 → 종료를 한 구간으로 검증 |
| 오늘 4×2 | 다음 적용. 초 숫자와 자정 경계, 시간대·날짜 보정 검증 |
| 집중 타이머 4×2 | 경과 시간 시계·일시정지·재개·재부팅까지 맞는 경우 확장. 벽시계로 단순 대체하지 않음 |
| 반복 시간 일정·자동 다음 일정 | 다음 회차/대상 선택과 상세 연결을 검증한 뒤 확장 |
| 이번 달·올해·주·분기·날짜 일정 | 일수 중심 표시 유지. 초 표시를 모두 추가하지 않음 |
| 기간 요약 4×1 | 단일 위젯 이후 오늘 칸만 검토. 3열 폭·큰 글자 검증 전 적용하지 않음 |

위젯 설정에는 해당 환경과 항목에서 제공할 수 있을 때만 ‘초 단위 표시’를 둔다. 지원 여부가 확인되지 않은 기기에 동작하지 않는 스위치를 보여주지 않는다. 기존 위젯은 현재 표시를 보존하고, 새 설정은 위젯별 별도 키로 저장한다. provider·선택 일정·형식 키·DB 스키마는 유지한다.

시간 표시는 예를 들어 `1:24:08 남음`, 1시간 미만은 `24:08 남음`으로 한다. 숫자와 상태는 같은 baseline, 숫자 열은 폭이 흔들리지 않게 구성한다. 추가 회전·깜빡임·숫자 진입 효과는 넣지 않는다. 팔레트·서체 역할·간격·눈금·글로우는 현 디자인 토큰을 따른다. 시계식 표현의 기존 단위 그룹과의 차이는 구현 승인 시 디자인 문서에 기록한다.

실시간 숫자와 정적인 눈금이 혼합된 시제품에서는 ‘눈금 기준 시각’을 구별한다. 최종 동적 렌더러는 같은 시간값으로 숫자와 눈금을 계산하는 것을 목표로 하되, 1초 정확도를 위해 60fps 연속 그리기를 요구하는 방식이면 전력 검증을 통과한 것으로 보지 않는다.

## 구현 구조

1. **공통 시간 계획 생성:** 위젯 ID, 원본 항목 ID, 회차 식별, 시작/종료, 현재 상태, 기준 시계, 정보 유효 기한, 설정 버전을 묶는다. `ScheduledTimeWindow`, `TimeDetailRange`, 집중 계산을 재사용한다. 상태를 표시 문구나 percent로 추정하지 않는다.
2. **값·상태 계산:** 진행 중인 값은 `max(종료 − 현재, 0)`으로 제한한다. 시작 전은 시작까지를 계산하고 시작 경계에서 상태를 함께 전환한다. 표시 초의 반올림은 앱과 비교해 결정하며 완료 판정은 실제 종료 시각으로 한다. 숫자가 먼저 0이 됐다는 이유로 완료 기록을 만들지 않는다.
3. **고정 구간의 종료:** 갱신 방송이 없어도 위젯 내부에서 0과 ‘종료’로 바뀌는지 검증한다. 알림과 DB 완료 처리는 기존 앱 로직이 수행한다. 위젯 그림 변경을 실제 완료 기록 저장으로 간주하지 않는다.
4. **정보 유효 기한:** 자정 이후의 오늘, 다음 반복 회차, 자동 선택은 이전 제목·범위를 새 시간처럼 재사용하지 않는다. 새 데이터가 필요한 시점에는 제한된 대기 표시와 갱신 동선을 사용한다. 오래된 회차의 상세를 새로운 일정으로 연결하지 않는다.
5. **시계 구분:** 일반 일정과 오늘은 실제 날짜·시간대 범위, 집중은 기존 경과 시간 시계를 따른다. Chronometer 비교안에서는 현재 벽시계와 경과 시간을 함께 읽어 기준을 변환하고, 시각 변경 시 다시 게시한다. 변환만으로 집중의 재부팅 복구가 해결된다고 가정하지 않는다.
6. **경계 예약:** 매초 알람 대신 필요한 시작·종료·자정의 가장 이른 경계를 예약하고, 처리 후 다음 경계를 계산한다. 이미 지난 경계는 현재 상태로 한 번에 정리한다. 기존 집중 알람과 중복 작업을 조정하되 알림 권한과 위젯 갱신을 분리한다. 위젯 표시만을 위해 새 정확 알람 권한을 필수화하지 않는다.
7. **게시 완료까지 보호:** `AppWidget`에 완료를 기다리는 갱신 경로를 두고, 경계 Receiver의 `goAsync()` 종료를 실제 게시 뒤로 옮긴다. 방송 처리 제한 내에서 끝내며 예외·취소에서도 정리한다. 동일 종료 방송의 중복 처리는 무해해야 한다.
8. **오래된 요청 무효화:** 편집·삭제·복구·위젯 제거 시 예약을 취소/재계산하고, 도착한 요청의 항목·회차·설정 버전을 다시 확인한다. 재부팅·시각/시간대 변경·앱 갱신에도 복구한다. 사용자가 강제 중지한 상황은 일반 프로세스 종료와 별도로 다룬다.
9. **렌더러 선택:** 정적 RemoteViews는 유지한다. 별도 동적 렌더러는 지원 버전·연산·검증된 환경을 만족할 때 선택한다. 앱에서 잡을 수 있는 생성/게시 오류는 정적 표시로 복구한다. 호스트 내부 오류가 항상 앱에 반환된다고 가정하지 않으며 검증되지 않은 환경을 기본 활성화하지 않는다.

Remote Compose 시제품은 가능하면 생성 전용 의존성으로 분리해 앱 전체 Compose 버전 변경을 피한다. 현재 Kotlin·Compose와 양립하지 않거나 내부 API 접근이 필수라면 그 비용을 먼저 기록하고 제품 코드에 편법을 추가하지 않는다. 새 XML 또는 동적 레이아웃에서도 기존 측정·최소 크기 정책과 실제 화면 공유 미리보기를 유지한다.

## 작업 순서와 통과 기준

**1. 작은 비교 시제품:** debug 전용으로 고정 시간 일정 하나에 기존 Chronometer와 동적 계산 두 경로를 비교한다. Remote Compose는 Android 16/API 36을 우선 검토하고, API 35와 기존 하위 OS의 대체 표시를 확인한다. 지원 버전 조회 결과·실제로 사용 가능한 공개 API/연산을 남긴다. 이 단계에서 전면 렌더러 교체를 시작하지 않는다.

**2. 가장 큰 실패 조건 확인:** 종료 직전 앱 프로세스 종료, 경계 방송의 의도적 지연/미전달, 화면 껐다 켜기에서도 음수 없이 종료하는지 확인한다. 분·시간 경계와 자정, 1초 미만 반올림도 포함한다. 하나라도 호스트 자체 처리로 충족하지 못하면 ‘정확한 초 위젯’의 기본 활성화를 보류한다. Chronometer에서 알려진 음수 문제가 재현되지 않았다는 몇 번의 결과만으로 제약이 없어졌다고 판단하지 않는다.

**3. 기존 위젯과 통합:** 통과한 범위에서 위젯별 옵션, A/시간 보드 렌더링, 경계 예약, 기준 시각 문구, 오류·정보 만료 상태, 상세 연결을 구현한다. 이후 집중의 단조 시계와 반복/자동 선택을 각각 확장한다.

**4. 사용자가 요청한 최종 검증:** 시간 계산·예약 무효화·중복 방송·부팅 복구의 의미 있는 테스트와 빌드/Lint를 실행한다. 실제 런처 검증을 별도로 수행한다. 테스트 소스나 Preview만으로 실제 위젯 동작을 완료 처리하지 않는다.
