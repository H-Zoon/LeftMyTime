# PointHome 인트로 → 리워드 알림 허용 플로우 (기획안)

작성일: 2026-10-19 · 상태: **§8 추천 기본값 6개로 확정, 결정 4(광고성 정보 동의 문구)는 자리만 구현.** 소스만 수정했고 빌드·Lint·테스트·실기기 검수는 미실행이다. 구현 기록은 §9.
관련 기록: [리워드 알림 수신 설정](REWARD_NOTIFICATIONS.md), [PointHome 플로팅 진입점](DESIGN_SYSTEM.md#pointhome-플로팅-진입점-2026-10-19), [원격 설정 키](FIREBASE_OPERATIONS.md).

## 1. 문제와 목표

**지금 사용자가 겪는 일:** 업데이트·설치 후 홈에 SDK 플로팅 버튼과 말풍선이 갑자기 나타난다. 무엇인지 설명이 없고, 리워드 알림 수신은 설정 → 알림 깊은 곳에 있어 발견하기 어렵다(기본 꺼짐).

**목표**
1. 사용자가 플로팅 버튼이 무엇인지 **한 번** 이해한다.
2. 원하는 사용자만 리워드·혜택 알림을 **명시적으로** 켠다. 권한 요청 직전에 이유를 읽는다.
3. 앱의 핵심 경험(열자마자 남은 시간을 읽기)을 막거나 늦추지 않는다.

**하지 않는 것:** 동의 기본값 변경(꺼짐 유지), 알림 허용을 앱 사용 조건으로 만들기, 보상 금액·지급 약속 문구, SDK 버튼 모형·캐릭터 직접 구현, 일정·집중 알림 채널 변경.

## 2. 현재 코드에서 확인한 제약

| 사실 | 출처 | 기획에 주는 영향 |
| --- | --- | --- |
| 첫 실행·온보딩 상태 값이 없다. 신규 설치와 업데이트 사용자를 구분하는 저장값이 없다 | 전체 검색, `UserPreferences` | 새 키 1개가 필요하다. 두 집단 모두 같은 키로 1회 처리한다 |
| 플로팅 버튼은 SDK가 Activity에 붙이며 위치를 앱이 알 수 없다. 앱은 모형을 만들지 않는다 | `PointHomeIntegration`, DESIGN_SYSTEM | 버튼을 가리키는 코치마크·화살표는 불가능하다. **글 중심 안내**로 한다 |
| `pointhome_entry_enabled=false`·자격값 누락·SDK 초기화 실패면 버튼이 없다 | `AppRemoteConfig`, `canUse` | 같은 조건에서는 인트로도 **표시하지 않는다**. 없는 버튼을 소개하면 안 된다 |
| 리워드 동의는 기기 내 설정(`reward_notifications_consent`, 기본 false), 시스템 권한과 별개다. 거부해도 동의값은 바꾸지 않는다 | `RewardMessaging` | 인트로도 같은 규칙을 따른다 |
| 알림 권한 요청 로직이 `SettingsActivity` 안에 private으로 있고, 편집 화면에도 리마인더용 별도 구현이 있다. 설정 이동 안내 문구는 "리마인더" 전용이다 | `SettingsActivity.selectRewardConsent`, `NotificationPermissionUi` | 세 번째 복사본을 만들지 않고 **리워드 동의 흐름을 공용화**해 설정과 인트로가 함께 쓴다 |
| 시스템 알림 권한은 일정·집중 알림에도 적용된다 | `strings` `settings_reward_permission_message` | 설명 문구에 반드시 포함한다 |
| 알림 터치로 PointHome을 여는 pending 경로가 있다 | `MainActivity` | 그 세션에서는 인트로를 띄우지 않는다. 이미 수신한 사용자다 |
| 분석은 파라미터 없는 `UsageEvent` 닫힌 목록. 리워드 기능은 새 이벤트를 추가하지 않았다 | `AppTelemetry`, REWARD_NOTIFICATIONS | 퍼널 측정 여부는 별도 결정(§8) |
| `docs/`는 GitHub Pages 공개 경로(`privacy.html`)다 | `.nojekyll`, `docs/` | 이 기획서는 `design/`에 둔다. 공개 경로에 두지 않는다 |

## 3. 제안 플로우

두 단계의 **하단 시트**(기존 `TimeDetailSheet`의 `ModalBottomSheet` 패턴 재사용), 단계 표시는 "1/2" 글자. 카드·일러스트·그라데이션·배지를 쓰지 않는다(v2).

```
홈 진입 ─ 표시 조건 통과? ──아니오──▶ 아무것도 하지 않음 (다음 진입에서 재평가)
   │예
   ▼
[1/2 소개] ──나중에/닫기──▶ 완료 처리, 재노출 없음
   │다음
   ▼
[2/2 알림 선택] ──받지 않기/닫기──▶ 동의 꺼짐 유지, 완료 처리, 설정 경로 한 줄 안내
   │알림 받기
   ▼
동의 저장(setConsent true)
   │
   ├ 권한 불필요(API 26~32) 또는 이미 허용 ─────────▶ 완료 안내
   ├ 13+ 미요청·1회 거부 ──▶ 시스템 권한 창 ─허용─▶ 완료 안내
   │                                        └거부─▶ "선택은 유지돼요" 안내 (동의 유지)
   └ 영구 거부·앱 알림 꺼짐·리워드 채널 차단 ──▶ 설정 안내 다이얼로그 ─열기─▶ 시스템 설정
                                                                  └취소─▶ "선택은 유지돼요" 안내
```

### 3.1 표시 조건 (모두 충족, 홈 `MainActivity`에서만)

1. `pointhome_entry_enabled`가 확정 true이고 자격값·SDK 초기화가 정상(플로팅 버튼이 실제 생성 가능).
2. 저장된 인트로 버전 < 현재 버전(최초 1).
3. 홈 로딩 완료, 생명주기 RESUMED, 다른 시트·다이얼로그·스플래시 전환 없음.
4. 이번 실행이 알림 터치 PointHome 진입이 아님.
5. 리워드 동의가 이미 켜짐이면 **1단계만** 표시(소개만 필요), 끝나면 완료.
6. 신규 설치의 첫 실행은 제외하고 다음 실행부터 표시(§8 결정 1의 추천안). 신규 설치와 업데이트의 구분은 저장값이 없으므로 `PackageInfo.firstInstallTime`·`lastUpdateTime` 비교 또는 "기존 일정 존재 여부"를 후보로 두고, 구현 단계에서 어느 쪽이 안정적인지 확인한다.

편집·백업·설정 등 다른 Activity 위에서는 띄우지 않는다.

### 3.2 화면 문구 초안 (ko, en은 구현 시 `values/strings.xml`에 함께)

| 위치 | 문구 |
| --- | --- |
| 1/2 제목 | 리워드 서비스가 새로 열렸어요 |
| 1/2 본문 | 화면에 떠 있는 ‘혜택 받기’ 버튼을 누르면 리워드와 혜택을 볼 수 있어요. 남은 시간을 보는 일에는 영향을 주지 않아요. (버튼 이름은 `pointhome_floating_message`를 인용하며 캐릭터·위치는 말하지 않는다) |
| 1/2 버튼 | 다음 · 나중에 |
| 2/2 제목 | 리워드 소식을 알림으로 받을까요? |
| 2/2 본문 | 새 리워드와 혜택이 생기면 알려드려요. 일정·집중 알림과는 따로 관리하고, 설정의 ‘리워드·혜택 알림 받기’에서 언제든 끌 수 있어요. 알림 권한은 앱의 다른 알림에도 적용돼요. |
| 2/2 고지(법무 확인 후 확정) | 광고성 정보 수신 동의 문구: 발신자, 전송 내용, 수신 거부 방법, 야간 전송 여부 (§8 결정 4) |
| 2/2 버튼 | 알림 받기 · 받지 않기 |
| 설정 안내(리워드 전용 신규) | 시스템 설정에서 알림을 허용해 주세요. 선택은 그대로 유지돼요. |
| 완료/유지 안내 | 기존 `settings_reward_ready`·`settings_reward_blocked` 문구 재사용 검토 |

- 두 버튼은 **같은 크기·같은 터치 영역(48dp 이상)**, 부정 선택을 숨기거나 흐리게 하지 않는다.
- "알림 받기" 완료는 **토픽 반영 요청**이지 수신 보장이 아니다. 완료 문구도 기존 정책대로 쓴다.
- 보상 금액·횟수·"받을 수 있어요" 단정 표현을 쓰지 않는다. 버튼은 SDK의 기본 말풍선(현재 `pointhome_floating_message`)을 그대로 쓰므로 본문은 그 문구와 모순되지 않게 한다.

### 3.3 저장 값

- `pointhome_intro_version` (Int, 기본 0). 시트를 어떤 방식으로 닫든 현재 버전으로 기록한다. 이후 새 캠페인이 필요하면 버전만 올려 재노출한다.
- 기기 내 설정이며 일정 백업으로 복구하지 않는다. 기존 키·DB 스키마는 바꾸지 않는다.
- 동의 변경 시각·계정 단위 동의 이력은 만들지 않는다는 기존 정책을 유지한다(§8 결정 4와 충돌 가능).

## 4. 상태·예외 표

| 상황 | 동작 |
| --- | --- |
| API 26~32 (런타임 권한 없음) | 권한 창 없이 채널 상태만 확인 |
| 13+ 권한 이미 허용 | 동의만 저장, 권한 창 없음 |
| 13+ 미요청 | 2/2에서 이유를 읽은 직후 시스템 창. 별도 설명 다이얼로그를 또 띄우지 않는다 |
| 13+ 거부(재요청 가능) | 기존 `shouldShowRequestPermissionRationale` 규칙으로 판단 |
| 13+ 영구 거부 / 앱 알림 꺼짐 / 리워드 채널 차단 | 설정 안내 → `ACTION_APP_NOTIFICATION_SETTINGS` 또는 채널 설정(기존 `openRewardNotificationSettings` 규칙) |
| 권한 거부·설정 안 열기 | 동의 켬 유지(기존 정책). "알림을 표시하려면 시스템 설정 허용 필요" 안내. 설정 화면에서 같은 상태가 보인다 |
| 시스템 창 위에서 회전·프로세스 종료 | 단계·진행 상태는 `rememberSaveable`. 복귀 시 `RewardMessaging.refresh()`와 권한 재확인 |
| 오프라인·토픽 반영 실패 | 시트를 막지 않는다. 설정의 기존 "다시 확인" 상태로 이어진다 |
| 시트 표시 중 원격 설정 변경 | 같은 프로세스에서는 시작 시 확정 값 고정(기존 규칙) |
| 큰 글자·긴 문구 | 본문 스크롤, 문구를 줄이거나 자르지 않는다 |
| TalkBack | 시트 제목을 heading, 단계("2단계 중 1단계")와 버튼 이름 제공, 닫기 후 홈 포커스 복귀 |
| 설정에서 이미 리워드 동의를 켠 사용자 | 1/2 소개만 |

## 5. 구현 단위 (승인 후)

1. **정책 함수**: 표시 여부를 순수 함수로 분리(원격 값·SDK 가용·인트로 버전·알림 터치·동의 상태·실행 횟수 입력). `RewardMessagingPolicyTest`와 같은 방식의 단위 테스트 소스 추가.
2. **저장소**: `pointhome_intro_version` 읽기/쓰기. 결정 1의 추천안을 택하면 "첫 실행 여부" 판단 값(실행 횟수 또는 설치/업데이트 시각 비교)이 추가로 필요하다.
3. **`PointHomeIntegration`**: 현재 private인 `initialized`/`canUse`를 읽기 전용 가용성 조회로 노출. 소개의 "버튼이 실제 있다"는 전제를 같은 기준으로 판단.
4. **리워드 동의 흐름 공용화**: `SettingsActivity`의 `selectRewardConsent`·권한 설명·설정 이동을 재사용 가능한 단위로 분리해 설정과 인트로가 같은 코드를 쓴다(회귀 위험이 있으므로 설정 동작을 먼저 고정).
5. **UI**: `ui/pointhome/PointHomeIntroSheet`(2단계, `TimeLeftTheme`·`Spacing`·`LayoutTokens`·`TimeLeftInlineButton` 재사용). `MainActivity`에서 호스팅.
6. **문자열**: ko/en 동시. 사용자 노출 문구는 `values`·`values-ko`만.
7. **디자인 갤러리**: debug `DesignGallery`에 실제 시트 재사용으로 1/2·2/2·설정 안내 상태를 로컬 상태로 표시. 실제 동의·SDK·시스템 설정을 바꾸지 않는다.
8. **문서**: `DESIGN_SYSTEM.md`(PointHome 항목에 인트로 규칙), `REWARD_NOTIFICATIONS.md`(인트로 진입점), `WORK_HANDOFF.md`, 문구가 바뀌면 `docs/privacy.html`.

외관 정리가 아닌 동작 변경(4번)은 별도 커밋 단위로 분리하고, 인트로 UI(5~7번)와 섞지 않는다.

## 6. 검증 계획 (사용자가 최종 검증을 요청할 때)

기본 명령 `./gradlew testDebugUnitTest assembleDebug lintDebug` 후 기기 확인:

- 표시 조건: 원격 false·자격값 누락·SDK 실패에서 미표시, 알림 터치 세션 미표시, 완료 후 재실행·회전·프로세스 복원에서 재노출 없음, 동의 이미 켜짐이면 1/2만.
- 권한 매트릭스: 허용·미요청·1회 거부·영구 거부·앱 알림 끔·리워드 채널만 차단, API 26~32 기기, 시스템 설정 복귀 후 상태.
- 실제 FCM 토픽 메시지 수신(동의 켬/끔), 일정·집중 알림 회귀.
- 밝게/어둡게, 320dp, 1.5배 글자, 영어/한국어, TalkBack, 시트와 SDK 플로팅 버튼의 겹침(스크림 위/아래 어느 쪽인지 실기기 확인 필요).
- 미검증 범위는 결과에 구분해 적는다.

## 7. 위험과 열린 확인

1. **광고성 정보 동의 요건**: 리워드·혜택 푸시가 광고성 정보에 해당하면 사전 동의 방식, 수신 거부 방법 고지, 야간 전송 별도 동의, 주기적 수신동의 재확인 같은 의무가 걸릴 수 있다. 앱 내 기기 단위 동의만으로 충족되는지, 서버 동의 이력이 필요한지는 법무·서비스 담당 확인이 필요하다. 이 문서 작성 중 최신 법령 원문은 확인하지 않았다.
2. **SDK 자체 동의 화면**: PointHome SDK가 최초 진입 시 약관·개인정보 동의 화면을 띄우는지 확인하지 못했다. 있다면 인트로 문구와 순서를 맞춰야 한다.
3. **시트와 플로팅 버튼 레이어**: SDK 버튼이 모달 스크림 위에 그려지는지 가려지는지 코드로 알 수 없다. 실기기 확인 후 문구("지금 보이는 버튼"은 쓰지 않음)를 확정한다.
4. ~~말풍선 문구 오탈자 의심~~ → 결정 6에 따라 한국어 `pointhome_floating_message`를 "혜택 받기"로 수정했다(영어는 원래 "Get benefits").
5. **퍼널을 볼 수 없음**: 현재 수집 항목으로는 인트로 노출·동의율을 알 수 없다.

## 9. 구현 기록 (2026-10-19, 소스만)

§8의 추천 기본값을 모두 따랐다. 결정 4는 `pointhome_intro_consent_notice`(ko/en)를 **빈 값**으로 두고, 값이 비어 있으면 시트가 표시하지 않는 자리만 만들었다. 문구와 서버 동의 이력 여부는 여전히 열려 있다.

| 영역 | 변경 |
| --- | --- |
| 표시 판단 | `pointhome/PointHomeIntroPolicy.kt` — 순수 함수 `shouldShowPointHomeIntro`, 저장소 `PointHomeIntroStore`(`pointhome_intro_version`, `pointhome_intro_home_launches`), 신규 설치 판정(`firstInstallTime`·`lastUpdateTime` 차이 1분 미만, 판정 실패 시 신규로 간주) |

기획과 다르게 정한 점:
- 설정 화면의 토글(`selectRewardConsent`)은 설명 대화상자를 유지한다. 공용화한 것은 판단 함수와 시스템 설정 Intent이며, 인트로는 시트에서 이미 설명했으므로 시스템 창을 바로 연다.
- 닫기(나중에·바깥 탭·뒤로)는 모두 완료로 기록하며 짧은 안내 토스트로 설정 경로를 알린다.
- 사용자가 시트를 연 채 프로세스가 종료되면 완료로 기록되지 않아 다음 실행에서 다시 보인다.

검증 결과(2026-10-19, `./gradlew testDebugUnitTest assembleDebug lintDebug`): 성공. Kotlin 컴파일 경고 0건, 단위 테스트 137개 통과(`PointHomeIntroPolicyTest` 6, `RewardPermissionPolicyTest` 5 포함). Lint 179건은 이번 변경이 새로 만든 것이 없고(첫 실행에서 나온 InlinedApi 2·UseKtx 2는 `@SuppressLint`와 `androidx.core.content.edit`로 수정) 나머지는 기존 경고다. 단, 설정 화면의 `POST_NOTIFICATIONS` InlinedApi 1건은 리팩터링한 줄에 있으나 같은 호출이 원래 받던 경고다.
