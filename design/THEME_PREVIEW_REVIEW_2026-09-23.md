# 테마 미리보기와 확장 구조 조사 — 2026-09-23

상태: **코드·공식 문서 조사와 제안. 앱 구현·디자인 기준 변경은 아직 하지 않음.**

후속 상태: 사용자 ‘진행’ 승인으로 **1단계 A 미리보기·적용/취소와 테마 정의의 기초**를 구현했다. 아래 내용은 구현 전 조사 기록이며, 실제 반영 범위·미검증 조건은 [구현 기록](QA_THEME_PREVIEW_2026-09-23.md)을 따른다. 새 계절 테마와 다른 레이아웃은 아직 제공하지 않는다.

사용자 요청: 설정의 화면 테마 선택에 미리보기를 제공하고, 계절별 색상부터 화면 구성이 크게 달라지는 테마까지 지원할 수 있는지 검토한다.

## 결론

모두 구현 가능하다. 현재의 밝기/강조색 미리보기는 기존 테마와 실제 화면 구성요소를 재사용할 수 있다. 글꼴·간격·눈금·레이아웃까지 다른 테마는 테마 정의와 화면 표현의 확장이 필요하다. A안 ‘시간 중심’을 기본으로 유지하면서, 사용자가 선택하는 별도 디자인을 지원하는 방향을 권한다. 새로운 디자인의 시각 규칙은 실제 구현 승인 시 해당 테마 범위로 문서화한다.

## 추천 미리보기 경험

설정에는 **‘테마’의 이름·현재 화면 모드·작은 화면 미리보기**를 한 영역에 둔다. 누르면 전용 미리보기 화면으로 들어간다. 테마는 비교할 시각 정보가 많으므로 큰 미리보기 영역을 확보한다. 정렬·만료·알림 등 일반 설정에는 이번에 정리한 드롭다운을 계속 쓴다.

1. 현재 적용값으로 미리보기 화면을 연다.
2. 상단에서 홈의 기간 요약·대표 시간·눈금·일정 행을 비교한다. 추후 목록·상세·위젯 보기로 전환할 수 있게 한다.
3. 디자인 테마, 그 테마가 지원하는 색상, 화면 모드(시스템/라이트/다크)를 고른다. 시스템 모드에는 현재 기기가 사용하는 밝기도 알려준다.
4. 선택은 미리보기 영역에만 반영한다. `적용` 시 선택 묶음을 저장하고 실제 앱·위젯을 갱신한다. 뒤로/취소는 기존 적용값을 유지한다.
5. 미리보기에서 상세 열기/일정 수정/삭제/위젯 추가는 실행하지 않는다. 화면 표시용 부분을 실제 화면과 공유하며, 눌러도 반응하지 않는 가짜 버튼으로 조합하지 않는다.

설정 화면을 보고 있는 동안 색이 바뀌는 것만으로는 큰 숫자·눈금·목록에서의 차이를 비교하기 어렵다. 미리보기는 이 앱의 대표 장면을 보여줘야 한다. 작은 이미지는 선택 안내용으로 쓰고 확대 화면에서는 실제 글자 배율·가용 폭으로 확인한다.

### 구현 시 주의할 상태 경계

- `ThemeSelectionDraft` 같은 임시 선택값과 저장된 선택값을 분리한다. 회전에는 임시값을 복원하되 저장은 `적용`으로만 발생시킨다. 여러 테마를 비교하는 동안 위젯이나 전역 야간 모드 설정을 갱신하지 않는다.
- 미리보기 하위에만 테마를 제공한다. Compose는 하위 구성 범위에 다른 테마 값을 제공할 수 있으므로 이 방식을 사용할 수 있다. [공식 CompositionLocal 설명](https://developer.android.com/develop/ui/compose/compositionlocal)
- 미리보기는 실제 데이터의 진입 시점 스냅샷을 사용한다. 비교 중 매초 숫자/정렬이 움직이지 않게 하고 ‘미리보기’임을 명시한다. 일정이 없으면 실제 기간 요약과 빈 상태를 표시한다. 하드코딩한 사용자 일정은 배포 코드에 넣지 않으며 검수용 가상 데이터는 기존 규칙대로 debug에 둔다.
- `HomeScreen` 전체를 단순히 축소하면 글자·터치 영역·접근성이 실제 앱과 달라진다. 먼저 대표 표시 부분을 상태를 입력받는 공통 구성요소로 분리한다. 실제 화면과 프리뷰가 같은 표시 코드를 사용해야 한다.
- 기존 `theme`, `color_theme` 저장 키와 값은 보존한다. 향후 디자인 ID는 별도 키로 도입하고 값이 없는 기존 사용자는 A 기본 디자인과 기존 색상을 해석한다. 잘못된/지원이 끝난 ID는 A로 안전하게 표시하되 기존 값의 자동 삭제는 피한다.

## 지원 범위와 난이도

아래 난이도는 코드 구조를 기준으로 한 상대 평가이며 일정 견적이나 실행 검증 결과가 아니다.

| 수준 | 예시 | 필요한 작업 | 상대 난이도 |
| --- | --- | --- | --- |
| 화면 모드·기존 색상 미리보기 | Clay의 라이트/다크 비교 | 임시 선택 상태, 공통 표시용 프리뷰, 적용/취소 | 낮음~중간 |
| 계절별 색상 | 봄의 옅은 배경·녹색 강조, 가을의 따뜻한 배경 | 테마별 전체 색상 역할, 밝게/어둡게 대응, 위젯 배경 | 낮음~중간 |
| 글꼴·숫자·눈금·표면 변경 | 숫자 서체, 눈금 형태, 간격, 절제된 질감 | 의미별 스타일 정의와 공통 구성요소의 사용 지점 | 중간 |
| 큰 레이아웃 변경 | 집중형 큰 시간 중심, 일정 흐름을 강조한 타임라인형 | 표현 방식 교체, 상태/행동 공유, 앱·위젯별 디자인 | 높음 |
| 탐색·동작까지 전부 달라짐 | 테마마다 다른 추가·수정·설정 경로 | 별도 제품 흐름과 넓은 회귀 검수 | 매우 높음; 초기 범위로 권하지 않음 |

Compose는 색상·서체·모양을 확장/교체하고 독자적인 디자인 시스템을 구성할 수 있다. 이 앱에서도 그런 구조를 사용할 수 있다는 판단이며, 레이아웃 변형 자체는 앱에 구현해야 한다. [공식 커스텀 디자인 시스템 안내](https://developer.android.com/develop/ui/compose/designsystems/custom)

## 장기 운영을 위한 구조 제안

서로 다른 개념 세 가지를 분리한다.

- **화면 모드:** 시스템/라이트/다크. 디자인과 별도로 유지한다.
- **디자인 테마:** 숫자·눈금·표면·레이아웃·움직임을 묶은 디자인. 안정적인 ID와 정의 버전을 가진다.
- **색상 변형:** 해당 디자인이 제공하는 검수된 색상 조합. 모든 디자인과 기존 색상의 무제한 조합을 만들기보다 테마별 지원 조합을 명시한다. A 디자인에서는 기존 6개 색상을 계속 제공한다.

구현은 다음 역할로 나눈다. 이름은 제안이며 이번 조사에서 클래스를 생성하지 않았다.

| 역할 | 책임 |
| --- | --- |
| `ThemeDefinition` / 테마 목록 | ID, 이름, 지원 색상, 밝게/어둡게 색상, 서체·표면·눈금·동작 스타일, 앱/위젯 표현 종류 |
| `ThemeSelection` / `ResolvedTheme` | 저장 선택과 실제 화면에 사용할 테마를 분리. 기기 밝기·지원 조합·기본값 해석을 한곳에서 수행 |
| `TimeLeftTheme` | 기존 Material 테마를 확장하고 필요한 스타일을 하위 화면에 제공 |
| 표시용 공통 상태 | 기존 시간 계산·대표 선택·목록 정렬 결과. 어떤 디자인에서도 같은 의미를 전달 |
| 화면 표현 방식 | 대표/기간/목록 등의 표시를 디자인별로 구성. 공통 상태·이벤트 계약을 사용 |
| 위젯 표현 방식 | 같은 테마 정의에서 위젯 색상/표면/눈금/크기별 배치를 파생 |

모든 화면을 테마마다 복사하지 않고, 작은 차이는 공통 스타일 값으로 처리한다. 구조가 실제로 다른 구역만 대체 표현을 만든다. 첫 단계에서는 기존 A 표현만 이 구조에 옮기고 두 번째 표현이 필요한 시점에 그 범위의 인터페이스를 확장한다. 범용 화면 생성기나 무제한 플러그인 구조를 선행 구축할 필요는 없다.

각 테마가 함께 지켜야 할 계약은 남은 시간의 의미, 경과 비율 계산, 오늘/달/년과 개인 일정의 접근성, 48dp 터치, 큰 글자·긴 제목, 사용자 선택 색상, 숨김 설정, 수정/삭제/위젯 추가 동선이다. 디자인별로 장식과 배치를 바꿔도 이 계약은 공통으로 검수한다. 테마 목록에는 적용 범위(앱/위젯)와 지원되는 미리보기를 명시한다.

초기 테마는 앱에 포함된 디자인으로 제공한다. 새 레이아웃은 앱 업데이트로 추가하고, 계절 테마는 우선 직접 선택하게 한다. 자동 계절 변경·원격 배포·다운로드 서체/이미지는 별도 요구가 생겼을 때 다룬다.

## 위젯을 함께 다루는 방식

앱은 Compose이고 설치 위젯은 RemoteViews이므로 화면 구현을 그대로 복사할 수 없다. 테마 정의와 계산 의미를 공유하고, 위젯에 맞는 단순한 형태를 별도로 제공한다. 앱 위젯에는 표시 요소와 제스처 제약이 있다. [공식 위젯 제약](https://developer.android.com/develop/ui/views/appwidgets/overview)

계절 테마가 배경색을 바꾸면 현재의 두 고정 배경 drawable도 확장해야 한다. 새 테마를 적용할 때 설치된 위젯과 추가 화면 미리보기를 함께 갱신하고 캐시에도 디자인 ID/버전을 포함한다. 기존 위젯 ID·내용 선택·일반 4×2/요약 4×1 기준을 유지하면서 실제 가용 크기에 맞춰 렌더링한다. 런처별 셀 크기 차이는 계속 별도 검수한다. [공식 크기별 위젯 배치 안내](https://developer.android.com/develop/ui/views/appwidgets/layouts)

위젯 표현이 아직 준비되지 않은 디자인은 앱 전용임을 명시하거나 위젯까지 준비한 뒤 제공한다. 처음부터 A와 첫 계절 테마를 앱·위젯 한 세트로 마무리하는 편을 권한다.

## 권장 진행 순서

1. **현재 A의 미리보기·적용/취소:** 실제 표시 구성요소 공유, 화면 모드·기존 색상 비교, 임시값 분리. 대표/기간/목록을 우선 보여주고 위젯은 실제 렌더러로 확인한다.
2. **테마 정의 정리 + 계절 테마 1개:** 기존 팔레트 유지, 전체 색상·위젯 배경을 포함해 끝까지 연결. 새 테마마다 AI가 따라야 할 범위와 검수 사례를 함께 남긴다.
3. **레이아웃이 다른 테마 1개:** 집중형 또는 타임라인형 중 하나의 실제 시안을 확정하고 공통 상태를 공유하는지 검증한다. 이 사례에서 필요한 만큼만 화면 표현을 확장한다.

최종 검수에는 기본/새 테마의 밝게·어둡게·시스템 모드, 320dp·큰 글자·한영·긴 제목·빈 상태·시작 전/진행/당일/만료, 미리보기 진입 전후 저장값 불변, 적용 1회/취소/회전, 위젯/미리보기 일치, 기존 사용자의 저장값 보존을 포함한다. 조합이 늘수록 검수 부담도 늘어나므로 검수된 조합만 제공한다.

이번 조사는 실행 성능·화면 적합성을 검증한 결과가 아니다. 빌드·Lint·단위 테스트·설치·실화면 검수는 실행하지 않았다. 기존 미커밋 구현은 그대로 두었고 A 디자인 기준도 변경하지 않았다.
