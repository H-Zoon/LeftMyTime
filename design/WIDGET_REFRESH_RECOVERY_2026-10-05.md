## 마지막 커밋 분석

`fc264dd859e9249816edb7c659cff87b51c8fbaf`는 다음을 추가했다.

- 정적 오늘·기간 요약·시간 일정·이전 복합 요약의 다음 15분 자체 갱신 요청.
- 기한이 지난 위젯 예약 보존과 위젯별 렌더링 오류 격리.
- 위젯 상세 진입 시 전체 위젯 갱신.
- 예약 계획 단위 테스트 소스와 미검증 조사 기록.

방향은 타당하지만, 성공적인 `updateAppWidget()` 뒤에 `record()`를 호출하고, 단 하나의 `AlarmManager.RTC` 일회성 알람을 다음 갱신으로 이어가는 구조였다. **기존 설치 앱에는 이 보완 자체가 포함되지 않은 상태**다. 수동 새로고침 성공은 자동 수신·백그라운드 실행·호스트 표시 중 어느 단계가 실패했는지를 확정하지 않는다.

## 코드로 확인한 공백

| 경로 | 문제가 되는 조건 | 이번 조치 |
| --- | --- | --- |
| 기존 설치 앱의 시스템 정기 갱신 의존 | 30분 `APPWIDGET_UPDATE`가 지연되면 정적 숫자가 그대로 남음 | 런처 갱신 방송과 별도로 WorkManager 영속 주기 작업 추가 |
| 성공 후에만 보조 예약 생성 | 최초 게시 실패·중간 프로세스 종료 시 아직 다음 예약이 없을 수 있음 | 게시 전에 주기 작업 등록을 기다림. 앱 시작·위젯 활성화 시에도 복구 |
| 일회성 알람 소비 후 재예약 | 전체 갱신 진입/위젯 목록 조회 단계의 예외로 재예약까지 도달하지 못함 | Receiver의 `finally`에서 재예약, 별도 영속 주기 작업으로 재진입 |
| 반복되는 `reschedule()` | 동일 PendingIntent의 `set()`을 계속 교체해, 이미 늦게 대기 중인 예약을 다시 미룸 | 같은 프로세스에서 이미 더 이른 알람이 있으면 유지. 수신·시간 변경 시 상태 무효화 |
| 지난 예약 + 곧 도래할 다른 예약 | 전체 최솟값이 과거이면 일괄 `현재+1분`으로 바꿔 2초 뒤 미래 경계까지 늦춤 | 각 예약의 재시도 시각을 계산한 뒤 최솟값 선택 |
| Android 15 등의 자동 선택 위젯 | 다음 후보의 경계 계산이 초 지원/옵션 조건 안에 있어 날짜 표시 중 시간 일정 시작을 놓침 | `Next`는 초 옵션과 무관하게 기존 경계 계획기 사용 |
| 위젯별 오류 격리만 있음 | 일부 위젯 실패나 데이터 읽기 오류 화면 게시를 작업 전체의 성공으로 취급할 수 있음 | 실패 결과를 집계하고 Worker가 재시도. 다른 위젯은 계속 갱신 |
| 앱 업데이트 시 복구 | 기존 `BootReceiver`는 집중/알림 복구가 예외를 던지면 뒤의 위젯 갱신도 건너뜀 | 위젯 provider도 `MY_PACKAGE_REPLACED`를 직접 처리 |

이 표는 코드에서 확인한 실패 가능 경로다. **보고된 과거 3시간 정지의 단일 원인을 기기에서 재현·확정한 결과는 아니다.**

## 절전 모드가 꺼져 있어도 지연되는 이유

배터리 절전 모드와 CPU 수면·Doze·앱 대기·비정확 알람의 일괄 처리는 서로 구별해야 한다. Android 12 이상의 `set()`은 별도 배터리 제한이 없어도 요청 시각보다 늦게 전달될 수 있다. `RTC`는 기기를 깨우지 않으며, 화면이 꺼지고 기기가 잠들어 있으면 예약 시각만으로 앱 실행을 보장하지 않는다. Doze 역시 절전 모드 스위치를 켜야만 진입하는 상태가 아니다. [공식 알람 안내](https://developer.android.com/develop/background-work/services/alarms), [Doze 안내](https://developer.android.com/training/monitoring-device-state/doze-standby).

30분 `updatePeriodMillis`도 정확한 시각 보장이 아니다. WorkManager는 위젯의 반복 갱신에 사용할 수 있지만 전력·대기 제약은 여전히 적용된다. [공식 위젯 갱신 안내](https://developer.android.com/develop/ui/views/appwidgets/advanced).

## 구현 범위

- `WidgetRefreshWorker` / `WidgetRefreshSchedule`: 실제 설치된 여섯 provider 전체에 대해 **고유 주기 작업 하나**를 사용한다. 최초 지연과 반복 요청은 15분, 실패 backoff는 1분부터 지수 증가다. 네트워크·충전·배터리 잔량 제약은 추가하지 않는다. `KEEP`으로 앱 재진입·렌더링 때 주기를 초기화하지 않는다. 모든 위젯을 제거하면 취소하고, 다른 provider에 위젯이 남아 있으면 유지한다.
- 영속 작업 등록은 렌더링 전에 완료를 기다린다. 스케줄러 자체의 오류는 로컬에 남기되 즉시 갱신은 계속한다. 앱 시작 때도 알림/일정 조회와 별도 코루틴에서 예약을 보완한다. 최초 등록 자체가 실패하면 다음 앱/위젯 이벤트에서 다시 등록하므로, 모든 스케줄러 실패를 극복한다고 보장하지 않는다.
- 기존 `AppWidget`, `WidgetBoundarySchedule`, `WidgetBoundaryReceiver`, `nextWidgetSelectionBoundary`, XML/초 렌더러, 수동 새로고침과 상세 진입 갱신을 재사용한다. 모든 단일/배치 갱신을 같은 오류 격리 경로로 모았다. Worker의 취소는 정상 전파한다.
- 기존 RTC 알람은 **비기상·비정확**을 유지하고 `setWindow()`의 10분 전달 창을 요청한다. 지난 예약은 재시도 요청을 유지한다. 실제 수신 전까지 더 이른 기존 알람을 보존한다. 이 창도 수면·Doze를 우회하지 않으며 15분 또는 25분 안의 실제 화면 반영을 보장하지 않는다. 프로세스 재시작 시 메모리의 예약 캐시는 새로 만들고 영속 주기 작업은 유지한다.
- 데이터 읽기 오류 화면이 게시된 경우에도 성공으로 끝내지 않고 다음 복구를 요청한다. 잘못된 사용자 일정 자체를 자동 수정하거나 삭제하지 않는다.
- 기존 Firebase의 위젯 이벤트는 `WidgetConfigured`만 있고 자동 수신/게시 이력이 없음을 먼저 확인했다. 추가한 로컬 Logcat은 provider 수신·경계 수신·주기 시작/종료·위젯 게시 제출·오류 종류를 구분한다. 새로 게시한 수동 새로고침 PendingIntent에는 표시를 붙여 `manual=true`로 구별한다. 일정 제목·내용·정확한 일정 날짜·일정 ID는 남기지 않는다. 로컬 위젯 ID와 상태 플래그만 기록하며 새 Analytics/Crashlytics 이벤트를 전송하지 않는다. `Widget submitted`는 API 호출 성공이지 런처가 새 화면을 그렸다는 증명이 아니다.
- 의존성은 `androidx.work:work-runtime:2.11.2`를 고정했다. 공식 AAR 메타데이터의 minCompileSdk 35 / AGP 8.6.0 / minSdk 23을 저장소의 36 / 8.10.1 / 26과 정적으로 대조했다. WorkManager의 기본 Startup 초기화를 사용하며 별도 Hilt WorkerFactory는 필요하지 않다. 라이브러리 manifest는 WAKE_LOCK·ACCESS_NETWORK_STATE·RECEIVE_BOOT_COMPLETED·FOREGROUND_SERVICE와 자체 컴포넌트를 병합한다. 새 런타임 권한 요청·전경 서비스 실행·정확 알람 요청은 추가하지 않았다. 최종 병합 manifest와 의존성 해석은 빌드 시 확인해야 한다.
- 앱의 일정 DB 스키마·저장된 일정·사용자 설정 키·출시 버전·시각 디자인은 바꾸지 않았다. WorkManager가 내부 작업 저장소를 사용하는 것과 일정 DB 스키마 변경은 별개다.

명시적인 최종 검증 요청 시:

1. `./gradlew testDebugUnitTest assembleDebug lintDebug`. 기존 경고와 새 문제를 구분하고 WorkManager 의존성·기본 초기화·최종 manifest를 확인한다.
