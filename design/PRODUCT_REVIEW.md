# 장기 운영을 위한 제품·디자인 검토

작성일: 2026-09-18.
최신 종합 평가는 [2026-09-25 제품·기능 개선 가능성 리뷰](PRODUCT_REVIEW_2026-09-25.md)를 따른다. 최신 커밋 빌드·에뮬레이터 확인과 코드상 위험, 우선순위·추가 기능 범위를 함께 기록했다. 아래는 개편 초기와 후속 결정의 이력이다.
2026-09-26 범위 결정: 사용자가 기기 간 동기화(F13)를 제외했다. 파일 백업·복구는 유지하며, 현재 범위와 남은 작업은 [종합 개선 적용 현황](IMPROVEMENT_IMPLEMENTATION_2026-09-25.md)을 따른다.
분석 범위: 저장소의 테마, 홈, 편집, 설정, 위젯 관련 코드와 실제 기기 홈 화면.
스토어 리뷰·이용 지표·경쟁 앱은 조사하지 않았다. “유일한 앱”, 인기의 원인, 개선 후 유지율은 검증된 사실로 단정하지 않는다.

후속 결정: 사용자가 짧은 시간 구간과 하루·달·년을 주요 용도로 확인했고, A/B/C 비교 후 **A안 ‘시간 중심’**을 확정했다.
아래의 발견·수정은 v1 정리 단계의 기록이다. 이후 디자인과 적용 순서는 [디자인 기준 v2](DESIGN_SYSTEM.md)가 우선한다.

## 판단

이미 `TimeLeftTheme`, `Spacing`, `Motion`이 있으므로 디자인 기반을 새로 만들 필요는 없다.
문제는 **정의되지 않은 역할과 화면별 구현의 차이를 발견하고 관리하는 절차가 부족한 것**이다.
AI가 기능 단위로 화면을 추가할 때 기존 기준을 찾기 어렵고, 기능 검증만 통과하면 시각적 차이가 쌓일 수 있는 구조다.

## 다음 우선순위

### 1. 홈에서 남은 시간을 확인하는 경험 정리

현재 상단의 오늘/월/년, 대표 일정, 같은 일정의 목록 표시, 검색·정렬·레이아웃 버튼이 한 화면에 있다.
대표 일정이 목록에 한 번 더 나오는 것은 오류가 아니지만, 반복 정보가 화면 공간을 차지한다.
홈의 정보 우선순위를 “현재 가장 중요한 남은 시간 → 내 일정 → 관리 도구”로 검토한다.

- 기존 이용자가 자주 보는 상단 정보·위젯을 먼저 확인한 뒤 구조를 조정한다.
- 검색·정렬을 보조 동작으로 옮기는 안과 현재 배치를 같은 데이터로 비교한다.
- 리스트·격자·대표 카드에 같은 시간 표기 원칙을 적용한다. 작은 화면에서 긴 시간 문자열이 잘리지 않게 한다.
- 현재 링은 경과 비율이고 숫자는 남은 시간이다. 사용자에게 의미가 전달되는지 확인한다.
- 기존 진행 표시 숨김 설정은 대표 카드에 적용되지만 목록의 링에도 일관되게 적용할지 검토한다.

완료 기준: 일반 이용자가 별도 설명 없이 원하는 일정의 남은 시간을 찾을 수 있고, 기존 자주 쓰는 동작의 접근성이 나빠지지 않는 것. “3초 내 확인”은 제품 목표 후보이며 현재 측정 결과가 아니다.

### 2. 디자인의 나머지 경계 정리

- 날짜/시간 입력은 `android.app.DatePickerDialog` / `TimePickerDialog`를 사용한다. Compose 팔레트와 다른 시스템 테마가 나타날 수 있다. 입력 방식·로케일·24시간 설정·날짜 경계를 검증하면서 공통 대화상자로 정리한다.
- 위젯은 XML/RemoteViews 색상과 레이아웃을 별도로 가진다. 같은 의미의 색상 매핑을 문서화하고 앱·위젯을 한 묶음으로 검수한다.
- 메타데이터 사용자 색상의 다크 테마 밝기를 보완했다. 전체 팔레트/사용자 색상 조합의 대비 수치 검증은 추가로 필요하다.
- 11–12sp 본문, 고정 높이 헤더, 2열 격자는 큰 글자에서 검증하고 필요한 경우 배치를 세로로 바꾼다.
- 다양한 팔레트에서 안 쓰던 Material 역할을 새로 사용할 때 기본 색상의 유입을 확인한다.

### 3. AI와의 작업 방식을 제품 운영에 맞추기

매 작업에 세 가지를 남긴다: 사용자 문제 한 문장, 사용할 기존 구성요소, 확인할 화면 상태.
AI에게 “예쁘게 바꿔줘”보다 “확정된 A의 시간 숫자·눈금·구분선 목록을 재사용하고 이 한 문제를 해결해줘”라고 요청한다.
다음 AI 세션도 기준을 읽도록 `AGENTS.md`에서 디자인 문서를 연결한다.

디자인 결정은 문서에서 관리하고 검증 화면은 실제 코드로 만든다. Figma 등 별도 도구가 필요해지면 같은 토큰과 구성요소 이름으로 맞춘다. 초기 단계에서 별도 디자인 파일을 유지하는 비용부터 늘릴 필요는 없다.

### 4. 출시 후 반응으로 다음 변경 결정

Firebase Analytics/Crashlytics 의존성은 있지만, 앱 코드에서 명시적인 `logEvent` 사용은 찾지 못했다. SDK 자동 수집·콘솔 설정·실제 수집 상태는 이번에 확인하지 않았다.

우선 기존 지표와 리뷰로 “시간 확인 / 일정 추가 / 위젯 사용 / 알림” 중 실제 사용 흐름을 확인한다.
필요한 경우 일정 생성 시작·완료 비율, 위젯 설정 완료, 오류 없는 이용 비율, 업데이트 전후 재방문을 측정한다. 일정 제목·내용·정확한 날짜는 이벤트에 넣지 않는다.
이벤트 정의와 수집 안내는 함께 검토하고, 이번 변경에는 새 수집을 넣지 않는다.

변경은 작게 출시하고 이전 버전 대비 오류·사용 흐름을 확인한다. 디자인 변화와 기능 변화를 한 번에 크게 섞으면 무엇이 영향을 주었는지 판단하기 어렵다.

## 현재 작업 순서 — A안 확정 후

1. A의 공통 색·서체·남은 숫자·시간 눈금을 구현하고 기준 화면 확인.
2. 홈 전체를 A로 전환하며 짧은 구간과 하루·달·년, 기존 일정 관리 동선을 함께 유지.
3. 입력·설정·대화상자를 같은 기준으로 전환하고 큰 글자·기존 설정 검수.
4. 위젯의 시간 의미·색상·작은 크기 표시를 맞추고 기존 위젯 설정 검수.
5. 검수한 화면을 기준으로 기능 추가 때마다 비교. 고정 시계·환경을 갖춘 뒤 필요한 범위의 이미지 비교 자동화.

A안의 홈·입력·설정·위젯과 debug 갤러리를 구현했다. [v2 검수 기록](QA_V2_2026-09-18.md)에 실제 확인 범위와 남은 조건을 기록한다. 이미지 수동 검수를 자동 회귀 테스트로 취급하지 않는다.

## 1차 커밋 이후 사용자 피드백

개인 일정과 오늘·달·년이 한 화면에 있어 산만하다는 피드백을 받았다. 사용자는 탭 분리를 제외하고 최상단의 작은 시간 흐름 위젯을 검토하도록 요청했다. [상단 시간 흐름 영역 분석](HOME_FOCUS_STRATEGY.md)에 세 기간 요약·상세 패널·크기와 상태 규칙을 정리했다. 후속 승인에 따라 카드 배경 없는 상단 세 기간 요약과 하단 상세를 구현하고 디자인 기준 v2에 반영했다. [후속 검수 기록](QA_FLOW_2026-09-18.md)에 화면과 확인 범위를 남겼다. 다음 일정의 시간 표기 축약은 별도 검토로 남긴다.


상단 요약 후속 피드백: 공통 상세 버튼을 제거하고 ‘각 기간을 누르면 자세히 볼 수 있어요’ 안내만 표시한다. 반복되는 기간별 화살표는 사용자 피드백에 따라 제거했다. 누른 기간만 직접 열며 마지막 기간 저장·복원 동작도 제거한다. 기존 값 자체를 삭제하거나 다른 사용자 설정을 바꾸지 않는다.

홈 전체 일정 진입은 상단 하나로 통합했다. 하단 ‘전체 일정 N개 보기’와 전용 문구를 제거하고, 기존 전체 일정 화면의 개수·검색·정렬은 유지한다. 최종 빌드·테스트 및 변경 화면 검수는 명시적 요청까지 보류한다.

전체 일정 화면의 보기 전환·검색·정렬 간격과 밑줄 검색 입력을 코드에 반영했다. 제목 입력과 공통 구성요소를 사용한다. 후속 사용자 요청에 따라 상세에 펼침 220ms·접힘 180ms의 높이·투명도 전환도 적용했다. 공유 일정 행을 쓰는 홈 다음 구간에도 같은 동작이 적용된다. [변경 및 조사 기록](ALL_SCHEDULES_REFINEMENT.md)에 근거와 최종 확인 조건을 정리했다. 빌드·Lint·단위 테스트와 새 화면·애니메이션 동작 검수는 명시적 요청까지 보류한다.

위젯의 크기별 기간 노출을 독립 항목으로 분리하는 방안을 [위젯 표시 항목 검토](WIDGET_CONTENT_STRATEGY.md)에 정리했고, 후속 ‘변경 진행’ 승인에 따라 코드에 반영했다. 기존 오늘·이번 달·올해 개별 선택에 ‘기간 요약’을 추가하고 개인 일정 아래의 자동 요약과 분리했다. 기존 설치 위젯의 표시를 보존하고 재설정 시 저장값을 복원하며, 설정 미리보기와 설치 위젯은 같은 렌더러를 사용한다. 런처 추가 목록의 목적별 개편은 후속 범위다. [구현 및 검증 대기 기록](QA_WIDGET_CONTENT_2026-09-18.md)에 새 표시 모드·빈 상태·화면 검수 조건을 기록했다. 최종 빌드·Lint·단위 테스트와 실행 검수는 아직 수행하지 않았다.

후속 [위젯 선택 방식과 설정 UI 조사](WIDGET_SELECTION_REVIEW.md)의 ‘개선 진행’ 승인에 따라, 선택 요약 중심의 설정 화면·검색 가능한 일정 선택·결과 예시가 있는 표시 형식·크기 부족 및 오류 안내를 반영했다. 런처는 오늘·이번 달·올해·기간 요약·내 일정의 다섯 용도로 구분하고 최초 선택과 미리보기를 연결했다. 기존 네 provider 식별자·저장값을 유지하며 내 일정 provider만 추가했다. 앱에서 바로 위젯을 추가하는 pin 기능과 자동 선택 알고리즘 변경은 후속 범위다. [구현 및 검증 대기 기록](QA_WIDGET_SELECTION_2026-09-18.md)에 적용 내용과 최종 검수 조건을 남겼다. 빌드·Lint·단위 테스트 및 새 실행 화면 검수는 아직 수행하지 않았다.

2026-09-21 사용자는 설치 위젯과 추가 목록·미리보기 모두 앱 디자인과 차이가 난다고 피드백했다. [위젯 디자인·기능 개편 전략](WIDGET_REDESIGN_STRATEGY_2026-09-21.md)에 숫자·단위 위계, 눈금, 두 가지 표현 계열, 미리보기 일치, 갱신 신뢰성·직접 상세 진입·상태 처리의 우선순위를 정리했다. **전략 제안이며 구현 승인·디자인 기준 확정·실행 검증으로 간주하지 않는다.**

2026-09-21 후속 ‘개편 진행’ 및 최소 크기 변경 승인에 따라 숫자·단위/눈금 공유, 최소 단일 250×200dp·요약 250×240dp·기본 4×3칸, 구형 작은 위젯 확대 안내, 생성/정적 미리보기, 표시 항목 상세 진입, 설정·오류 상태·자동 선택 경계 및 시간 변경 갱신을 구현했다.
